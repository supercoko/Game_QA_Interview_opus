## 2. 追问树

### 树 1：DataTable 变更检测——链路与可靠性（面试官 B 重点）

**L1 问：讲一下 DataTable 变更检测。**

**答**（✅ 按简历内容组织）：策划改了 DataTable 之后，QA 很难及时知道改了什么、影响谁。我设计了一条检测流程：Perforce 的 change-commit 触发器把提交的 CL 号传给 Jenkins；执行机用 UGS 同步到这个 CL，调用程序提供的蓝图接口把 DataTable 导出成 JSON；用 DeepDiff 和上一个成功快照对比，CL 和快照关联存进 MongoDB；变更在 Web 上展示，再按飞书多维表格里「资源路径 → QA」的映射通知对应的人。除了导出接口，触发、编排、差异计算、存储、展示、通知都是我做的。

> 面试官在验证：是不是你做的，职责边界清不清楚。

**L2 问：为什么用 change-commit 触发，不用 change-submit 或者定时轮询？**

**答**（✅ 原理；⚠️ 触发器是谁配的、有没有按路径过滤，要按实际说）：change-submit 在文件真正提交前触发，适合做拦截校验，那时变更还没落库；change-commit 在提交成功后触发，CL 号已经确定，适合「通知已经发生的变更」。和定时轮询比，事件触发延迟低，也不会空跑。另外 trigger 脚本只负责把 CL 号交给 Jenkins，必须马上返回，不能在 trigger 里做重活，否则会拖慢所有人的提交。触发器表还可以按 depot 路径过滤，只有 DataTable 目录的提交才触发。

> 面试官在验证：你懂 P4 触发器的类型，知道不能阻塞服务器。

**L3 问：为什么要同步工程、起编辑器导出？直接解析文件不行吗？**

**答**（✅）：DataTable 是 .uasset 二进制，序列化格式和行结构体定义、引擎版本绑定，脱离引擎很难可靠解析。用引擎导出 JSON，结构体、枚举、软引用都会按引擎的语义序列化出来，结果可信。代价是慢：每次都要同步，再启动编辑器。UGS 的作用是同步到指定 CL，⚠️ 如果项目配置了预编译二进制，编辑器启动时就不用本地编译（按你们的实际情况说）。

**L4 问：一次跑多久？为什么串行？提交多的时候积压怎么办？**

**答**：

- 耗时：[填写：同步约 X 分钟，导出约 Y 分钟；高峰期队列最长排过多少]。
- 串行的原因（✅ 原理，⚠️ 核对当时的考虑）：一台执行机一个工作区，并行会互相覆盖同步结果；更关键的是，差异是和「前一个成功快照」比的，乱序执行会让差异归属错乱。
- 积压的改进方向（⚠️ 当时做了的说做了，没做的说是改进思路）：
  1. **增量导出**：用 `p4 describe -s <CL>` 拿到这次改动的文件列表，只导出改了的表，不全量导出；
  2. **队列合并**：积压时把多个 CL 合并成一次导出，差异标成「CL 区间」，牺牲单个 CL 的归属，换吞吐；
  3. **减少启动开销**：把导出封装成 commandlet，或者用常驻的编辑器进程，不必每次冷启动。

**L5 问：CL N 的任务失败了，你人工重跑之前，CL N+1 已经跑完了，差异算谁的？**

**答**（这是这套设计最容易被抓的漏洞，一定要准备）：

- 按「和前一个成功快照比」的逻辑，N+1 的差异实际包含了 N 和 N+1 两次改动，归属会错。
- 正确的做法（⚠️ 当时没做就说是现在的改进思路）：快照按 CL 号存储；差异永远和「CL 号小于当前、最近的一个成功快照」比；N 重跑成功后，重新计算 N+1 相对 N 的差异，更新展示，并补发通知（或者在 N+1 的结果上标注「包含 CL N 的改动」）。
- 失败恢复：网络、同步这类临时性失败应该自动重试几次；导出报错这类确定性失败才需要人工处理。任务要以 CL 号做幂等，重跑不会产生重复快照和重复通知。

> 面试官在验证：你有没有想过系统在异常情况下的一致性。能主动说「当时这里有缺陷，我现在会这样改」，是加分项。

### 树 2：DataTable 变更检测——差异质量与价值（A、B 都会问）

**L1 问：DeepDiff 比较 DataTable 的 JSON，有没有遇到什么坑？**

**答**（✅ 常见坑；⚠️ 说你实际遇到并处理过的）：

1. DataTable 导出的是行数组，直接比数组的话，中间插一行，后面所有行都会显示为「变了」。要先转成以 RowName 为 key 的字典再比。
2. 浮点数精度噪音：用 DeepDiff 的有效位数或容差参数。
3. 无意义的字段（时间戳、GUID 之类）要排除掉。
4. DeepDiff 原始输出人看不懂，要转成「表 / 行 / 字段：旧值 → 新值」。

**L2 问：通知会不会太多，QA 被刷屏以后干脆不看了？**

**答**：按资源路径只通知相关的 QA；短时间内发给同一个人的多条可以合并；消息里只放摘要和 Web 链接，不塞全部差异。[填写：有没有做合并？有没有人反馈过太吵？]

**L3 问：「资源路径 → QA」的映射谁来维护？漏配了怎么办？**

**答**：[填写：谁维护]。兜底思路（✅）：没匹配上的路径发给默认负责人或者群，不能静默丢掉；定期输出「未映射路径」清单，让映射表跟着目录结构更新。

**L4 问：QA 收到通知以后做什么？举一个通过它发现问题的真实例子。**

**答**：[填写：一个真实例子，最好是「策划改了 X 字段 → QA 收到通知 → 发现影响了 Y」]。没有明确例子的话，就如实说它主要提升了感知效率，再给出你能确认的数字（每天处理多少 CL、覆盖多少张表）。**不要编例子。**

**L5 问：这个工具的价值怎么衡量？现在让你重做，你会怎么改？**

**答**：

- 指标：覆盖的表数、日均处理的 CL 数、端到端延迟（提交到通知）、通知准确率、由此发现的问题数。[填写你有的]
- 重做方向：
  1. 增量导出、自动重试、以 CL 做幂等（见树 1）；
  2. **从「告诉你变了」升级到「告诉你变得对不对」**：在差异上叠加规则校验，包括引用的 ID 是否存在、枚举是否合法、数值是否越界（比如堆叠上限只能是 -1 或 ≥1，这就是树 7 里的那类问题）；
  3. 把差异和回归范围关联：改了哪张表，就推荐回归哪些模块和用例。上线数据里有 14.5% 的问题理论上靠静态检查就能拦住（见 [01](01_上线Bug模式分析.md) 发现 6）。

> 第 2 点是从「变更感知」到「变更校验」的升级思路，测开面试官会很感兴趣。

### 树 3：内部质量工具平台与 AI 辅助重构（面试官 B 重点）

**L1 问：讲一下内部质量工具。基于哪个开源框架？你具体做了什么？**

**答**：[填写：框架名称、为什么选它]。平台整合了 Checklist、自动化结果、配置 Diff 和问题反馈；我开发了提交工具的单据关联、状态和提交人检查，以及任务提醒。

**L2 问：提交检查具体检查什么？为什么需要？**

**答**（⚠️ 按实际规则说）：提交时检查这个 CL 有没有关联单据（需求单或缺陷单）、单据状态允不允许提交（比如缺陷单是否处于修复中）、提交人是不是单据的负责人。目的是让每次提交都能追溯到单据，QA 回归时知道这次改动对应哪个问题，也能防止修复绕过流程直接合入。[填写：检查不通过时是拦住提交，还是只提醒？]

**L3 问：开发会不会嫌麻烦？怎么推广的？**

**答**（✅ 思路；[填写] 真实阻力）：规则分级，有的只警告、有的才拦截；留紧急通道（比如线上热修可以先提交后补单）；报错信息写清楚怎么改；推广时先找团队负责人拿到流程上的支持。[填写：真实遇到的反对意见，以及你怎么处理的]

**L4 问：「AI 辅助重构」具体怎么用的？怎么保证没改坏？**

**答**：[填写：用的什么工具，重构了哪部分，比如拆分大函数、统一接口、生成接入代码]。保证正确性（✅）：

1. 重构前先准备对比用例，同一输入下新旧版本的输出要一致；
2. 小步提交，每一步都能回滚；
3. AI 改的代码逐段人工 review，不整段照搬。AI 常见的问题是编造不存在的 API、漏掉边界处理；
4. 接入新平台时先灰度，小范围用一段时间再全量。

**L5 问：你怎么看 AI / Agent 在测试工具里的应用？**

**答**：先找「结果能验证」的场景，比如配置差异的自然语言摘要、缺陷单自动归类后由人确认；固定一份评估集，每次改提示词或模型都重跑评估；规则方案作为基线和对照组。可以接着讲 `bug_insight` 的规划（[04 方案八](04_自动化与工具方案_UE主线.md)）。

### 树 4：FlowGraph 静态检查（A、B 都会问，和任务测试强相关）

**L1 问：FlowGraph 静态检查做了什么？**

**答**：⚠️ 先用一句话说清楚 FlowGraph 在你们项目里是什么（任务流程、关卡事件，还是别的）。我负责把 XML 解析成 JSON、编写一部分节点的 Python 检查规则，以及结果入库、Web 展示和飞书通知。

**L2 问：举几条你写的规则。**

**答**：[填写：你真实写过的规则]。参考方向（✅ 挑你做过的说）：

- 必填参数为空；
- 引用的 ID（任务、道具、NPC、对话）在配置表里不存在；
- 孤立节点或不可达节点；
- 输出端口没连线，流程走进死路；
- 有环但没有退出条件；
- 节点参数类型和节点类型不匹配。

**L3 问：为什么先转成 JSON？**

**答**（⚠️ 按实际原因）：XML 里层级和属性混在一起，规则写起来很绕；统一成「节点列表 + 连线列表 + 参数字典」的 JSON 结构后，规则只需要关心图结构和字段；JSON 也方便存库和在 Web 上展示。

**L4 问：误报多吗？一共拦下过多少问题？**

**答**：[填写：规则数量、拦截数量、误报情况]。处理误报的思路（✅）：规则分级；对确实是故意这样设计的节点加白名单；报错定位到「图名 + 节点 ID」，让策划能直接找到。

**L5 问：静态检查和任务的动态测试怎么分工？**

**答**（✅ 结合上线数据，是很好的收尾）：静态检查管「结构合不合法」，比如引用是否存在、流程有没有死路；动态测试管「运行时行为」。上线数据里，原神 5.1「黑岩之困」在巡查目标阶段就提前击败相关敌人，导致后续目标无法进行；原神 7.1 在接任务前清除了碎冰，导致任务无法继续。这两张图的结构都合法，静态检查发现不了，要靠动态测试里「提前完成」「前置世界状态」这类维度（见 [09 任务部分](09_战斗与任务通用方法论.md)）。反过来，「引用了不存在的 NPC」这种问题，静态检查几秒钟就能发现，不应该留给人工去测。

### 树 5：基础战斗冒烟（A、B 都会问）

**L1 问：讲一下战斗冒烟。**

**答**：用 UE Functional Test 编排角色和怪物的基础攻击，通过程序和中台提供的接口控制 AI、触发攻击，再读取生命值做断言；接入 Jenkins，用 Python 提取失败信息、推送通知，同时保留完整日志。[填写：一共覆盖多少个角色或怪物、多久跑一次]

**L2 问：只断言生命值有没有减少，够吗？**

**答**（⚠️ 按实际断言方式说）：冒烟的目标是验证链路通：攻击能命中、伤害能结算、死亡能触发，所以断言的是生命值的变化。要验证数值就不够了：精确断言需要先控制住随机性（暴击、伤害浮动），还要有公式算出的期望值。冒烟和数值回归是两层不同的东西，我当时做的是冒烟这一层。

**L3 问：用例稳定吗？不稳定的原因有哪些？**

**答**（✅ 常见原因；⚠️ 说你实际遇到的）：场景或资源没加载完就开始测；AI 行为有随机性；物理或寻路导致打不中；帧率不同导致时序变化。处理方法：用条件等待（角色就位、AI 状态就绪）代替固定时长等待；通过接口直接触发攻击，不依赖 AI 自己决策，这也是要用程序提供的 AI 控制接口的原因；固定出生点和朝向。

**L4 问：在 Jenkins 里怎么跑？失败信息怎么提取？**

**答**（✅ 通用做法；⚠️ 按实际说）：用命令行启动编辑器，跑指定的测试（`-ExecCmds="Automation RunTests ..."`），导出报告目录；Python 解析 UE 导出的报告 JSON 或日志里的错误行，汇总后推送飞书，附上完整日志的链接。

**L5 问：发现过什么问题？如果继续做，下一步做什么？**

**答**：[填写：一个真实发现，比如某次提交导致攻击无法命中]。下一步：

1. 数据驱动：角色、怪物、技能列表从配置里读，覆盖面随配置自动增长；
2. 从冒烟升级到数值基线：固定随机种子，读战斗事件日志而不是 UI 上的数字，和上个版本的基线做差异比对；
3. 结合上线数据，优先加「状态进出」和「多实例」检查。比如原神 2.6，多人模式下两个七七，治疗量按另一位玩家的攻击力计算（见 [04 方案三、四](04_自动化与工具方案_UE主线.md)）。

### 树 6：采集物自动化（面试官 B 重点）

**L1 问：讲一下采集物自动化。**

**答**：读取采集物配置里的坐标和朝向，用 GM 传送过去、调整相机，再用 Poco 找到交互控件点击；用控件状态和奖励弹窗判断是否成功；保留日志、截图、录像和 Airtest 的 HTML 报告。这是阶段性实现，特殊场景覆盖有限。[填写：覆盖了多少个，总共有多少个]

**L2 问：为什么用控件和弹窗判断，不读背包数据？**

**答**（⚠️ 先说当时的真实原因，比如当时没有可用的数据查询接口）：表现层断言覆盖了玩家实际看到的东西，但缺点是不稳定，而且分辨不出「弹窗弹了但数量是错的」。更好的做法是双重断言：表现层加数据层（用 GM 查询采集前后背包数量的差值）。

**L3 问：传送过去后失败，常见原因有哪些？**

**答**（✅；⚠️ 说你遇到的）：场景流式加载还没完成；落点在地面以下或者在物体里面；交互提示依赖距离和朝向，所以要调整相机和朝向；采集物已经被采过或者在冷却中；有别的弹窗挡住。对应的处理：等加载完成的条件、传送后校验角色位置、先清理弹窗、用 GM 重置采集物状态。

**L4 问：特殊场景为什么覆盖不了？**

**答**：[填写：比如需要特定任务进度、天气或时间、机关解开后才出现；在水下、高处或副本里]。这些需要先构造前置状态（用 GM 设置任务进度、时间），成本高，所以第一阶段先覆盖普通场景。

**L5 问：这类大世界交互的自动化，怎么判断值不值得做？**

**答**（✅）：采集物数量多、每个版本都在新增、配置坐标经常改，回归次数多，自动化的收益就高；但表现层断言的维护成本也高。最值得做的是批量巡检「配置的坐标能不能到达、能不能交互、发不发奖」。上线数据里原神「位置/地形」类问题在战斗模块里占 6.3%，说明大世界的位置问题确实会漏到线上。

### 树 7：背包 / 快捷背包与 -1 无限堆叠（面试官 A 重点）

**L1 问：背包你测了哪些内容？**

**答**：物品、背包、快捷背包和相机。背包部分覆盖堆叠、容量、排序筛选、快捷绑定；同时关注在不同角色状态、任务进度和场景切换下，操作逻辑和数据是否一致。

**L2 问：讲一下 -1 无限堆叠的问题是怎么发现的。**

**答**（⚠️ 现象细节按实际补充）：背包和快捷背包的角标显示有问题，程序给出的修正方案是「按配置的堆叠上限判定」。我对照策划的规则，又看了 Lua 实现，发现修正方案没有考虑配置里的 -1，也就是「无限堆叠」这个特殊值，按普通上限处理会判断错。[填写：具体会错成什么样]。我把这个遗漏反馈给程序，跟进修复。

**L3 问：你为什么会去看 Lua 代码？QA 看代码的边界在哪？**

**答**：修正方案描述的是规则，我要确认实现覆盖了这个配置字段的所有取值。看代码的目的是确认等价类有没有漏，不是替程序改代码。能读懂判断逻辑、找到这个字段在哪些地方被用到就够了，结论要和程序当面确认。

**L4 问：堆叠上限这个字段，你会怎么设计测试数据？**

**答**（✅）：

- 取值：1（不可堆叠）、普通值 N、N-1 / N / N+1、-1（无限）、0（需要先和策划确认是否合法）、超大值（数字位数显示会不会溢出）；
- 场景：拾取时刚好满、溢出时怎么拆分；背包和快捷背包里同一物品的角标是否一致；用到 0 时快捷栏的绑定怎么处理；排序时无限堆叠的物品排在哪。

**L5 问：怎么防止同类问题再出现？**

**答**：

1. **配置检查**：加一条规则，堆叠上限只允许 -1 或 ≥1；
2. **代码层**：建议程序把「是否无限」封装成统一的函数，不要到处直接判断 -1；
3. **用例设计**：整理一份「魔法值字段清单」（-1、0 这类有特殊含义的取值），写用例时逐个检查；所有读这个字段的功能（背包、快捷栏、商店购买、邮件领取、合成）都要回归。

上线数据里边界值类问题的功能错误比例接近一半（S1+S2 占 46.1%）。比如崩铁 2.6，背包物品数量达到上限时，有概率无法进入部分关卡：一个系统的边界状态卡住了另一个系统。

### 树 8：死亡与升级同时触发（面试官 A 必问，最强故事）

**L1 问：讲一下这个问题。**

**答**：角色死亡和升级同时触发后，使用药品没办法把生命值回满。我先找到稳定复现的方法，再结合服务端日志和代码定位：死亡校验的分支跳过了属性同步，升级带来的最大生命值提升没有同步过来，药品回复时用的还是旧的最大生命值。和程序确认原因后，跟进了修复。

**L2 问：「同时触发」这种情况，你是怎么稳定复现的？**

**答**：[填写：你的真实方法]。可以参考的思路（⚠️ 只说你真的做过的）：用 GM 把经验调到离升级差一点；找一个「击杀得到经验」和「角色死亡」能同时发生的场景，比如同归于尽、持续伤害；或者用 GM 同时触发两件事；多试几次，找到稳定的时间窗口。关键是把「偶尔出现」收敛成「必现条件」。

**L3 问：你是怎么从日志定位到「跳过了属性同步」的？**

**答**（⚠️ 按真实细节）：把正常升级和「死亡 + 升级」两种情况的服务端日志放在一起对比，正常升级会有属性同步、最大生命值更新的记录，异常的情况里这一条没有；再到代码里找死亡处理的分支，发现它跳过了同步。[填写：你看的是哪部分日志、代码是什么语言、程序当时怎么回应的]

**L4 问：修复方案你会提什么建议？回归要测哪些？**

**答**：修复方式由程序决定，我会追问一个问题：死亡分支里**还跳过了哪些同步**？不只是最大生命值，攻击、防御、Buff、经验、等级本身都可能受影响。回归范围：死亡时同时发生的其他属性变化（换装备、Buff 到期、升级、天赋解锁）；复活后的属性；断线重连后的属性；多人场景下其他玩家看到的数值。

**L5 问：从这个问题里，你总结出了什么方法？**

**答**：它是一个「两个状态变化在同一时刻发生」的时序问题。我后来把它整理成一个检查维度：对关键的状态变化（死亡、升级、换装、进出场景、切角色）做两两同时触发的组合。上线数据里时序类问题有 215 条，功能错误比例 47%。比如原神 3.4，攀爬时在体力耗尽的瞬间打开背包，退出后角色有概率一直保持攀爬状态；终末地莱万汀在终结技即将结束的瞬间放战技，会让终结技提前结束。现在我在需求评审时会专门问：「这个状态变化和死亡、升级、切场景同时发生时，谁先处理？」

> 这棵树能完整体现「发现 → 复现 → 定位 → 推动 → 举一反三」的闭环，是业务岗面试里最该讲透的故事。

### 树 9：相机测试（面试官 A）

**L1 问：相机测了哪些？**

**答**：跟随、遮挡、锁定、回正。[填写：每一项的一个具体测试点或者发现过的问题]

**L2 问：遮挡怎么测？怎么判断是 bug？**

**答**（✅）：场景类型包括墙角、窄通道、植被、半透明物体、门、低矮的室内、贴着墙转身。**先和策划、程序确认标准**：被遮挡时，是拉近相机、让遮挡物半透明，还是保持不动？有标准，才能判断是不是 bug。几类客观问题：相机穿进模型内部看到背面、角色被完全挡住、相机来回抖动或者弹跳。

**L3 问：锁定测什么？**

**答**（✅）：锁定目标怎么选（距离、角度、优先级）；切换目标；目标死亡、离开范围、隐身后的处理；多个目标；锁定状态下闪避、冲刺、放技能时相机的表现；锁定加遮挡；键鼠和手柄的锁定方式差异。

**L4 问：相机这种「手感」问题，怎么提单才不会被打回？**

**答**：把客观问题（穿模、卡住、抖动、回正失效）和主观体验（速度、距离）分开。客观问题附上录像和复现条件（场景、位置、操作）；主观体验作为体验建议提给策划，附上对比（同项目其他场景，或者同类游戏的做法），不和 bug 混在一起提。

**L5 问：相机测试能自动化吗？**

**答**（✅ 思路）：一部分可以。在场景里批量放探测点，自动检测相机和角色之间是否被遮挡、相机是不是卡在碰撞体里面、相邻两帧相机位移是否突变（抖动）。还要注意相机改动会影响别的玩法：原神 3.1，镜头默认距离被修改后，魔神任务「缄默的求知者」无法完成。所以相机参数改了，依赖视角的玩法都要回归。

### 树 10：《无限暖暖》新手引导与手柄 / PS5（面试官 A；鹰角系统向也会问）

- 引导中途被打断（死亡、断线、切后台、强制剧情）后能不能恢复；

**L3 问：你发现的「引导卡住」和「互斥异常」具体是什么？**

**答**：[填写：真实的现象、触发条件，以及你怎么发现的]

**L4 问：手柄测试和键鼠有什么不一样？PS5 冒烟测了什么？**

**答**：手柄要关注：按键提示图标会不会跟着设备切换；焦点导航能不能到达每个可操作的元素；引导要求的操作在手柄上能不能完成（比如要求鼠标点击某个高亮区域）；中途切换设备。PS5 冒烟：[填写：启动、登录、主界面、哪些基础系统]。⚠️ 如果没有参与主机提审和合规测试，就直接说没有，不要被追问带着走。

| Jenkins 执行机挂了怎么办？                        | 任务状态持久化；以 CL 做幂等；恢复后从最后一个成功的 CL 继续补跑；监控告警                                                       |
| 怎么证明你的工具值这个人力？                      | 发现问题数 × 问题在后期才发现的修复成本，对比工具的开发和维护成本；用户使用频次；如果没有统计，就说明当时没做度量，以后会怎么做 |
