## 一、定位：怎么讲自己

### 核心叙事

> 「我有三年在研项目的测试经验，一半做系统功能测试，一半做质量工具。项目没有上线，这是我的短板，我很清楚。所以我做了一件事来补上线视角：把四款上线游戏至今 的 4000 多条修复记录做成结构化数据，写了分析工具，归纳出线上缺陷的触发模式，再把结论反哺到自己的测试设计方法和工具规划里。」

这段话的作用：

1. **主动承认短板**，面试官就不用再花时间试探这一点；
2. **紧接着给出你为补短板做的具体行动**，而且这个行动有产出、有数据，经得起深挖；
3. 把话题引到你**准备充分的领域**：缺陷模式、测试设计、工具。

### 雷区

| 不要这样做                                          | 原因                                                                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 声称参与过上线项目，或者暗示公告里的 bug 是你发现的 | 一问细节就露馅，而且是诚信问题                                                                                       |
| 把公告分析说成「公司内部数据」                      | 同上；说清楚是公开数据，反而说明你有主动性                                                                           |
| 把「为什么漏测」的推测说成事实                      | 你没有内部信息。说「我推测」，再说明推测依据，这本身就是严谨的表现                                                   |
| 背方法论但不举例                                    | 面试官听过太多遍「等价类、边界值」。你的优势是每个方法都有真实案例                                                   |
| 抱怨前项目「很水」「被上游卡住」                    | 可以客观说明「项目中后期受上游进度影响，测试内容有限，所以我把精力投在了工具和方法沉淀上」，前提是**这是真的** |
| 每个问题都往数据分析上扯                            | 被问到具体技术问题时，先正面回答，数据只作为佐证                                                                     |

## 三、项目经历（STAR）

### 故事 A：上线缺陷模式分析工具（已经完成，可以直接讲）

> 面试前务必自己跑一遍、读懂每个文件；最好再改一个规则，并补上对应的测试用例。被问到「这段代码你怎么写的」时，必须答得上来。

|                  | 内容                                                                                                                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S** 背景 | 在研项目没有上线经验，缺乏「线上会出什么问题」的直觉，测试设计主要靠经验和需求文档                                                                                                                                                                                                                         |
| **T** 目标 | 用公开数据建立对线上缺陷分布的认知，并转化成可用的测试设计清单                                                                                                                                                                                                                                             |
| **A** 行动 | ① 收集四款游戏 111 篇公告的修复条目；② 写解析器，用公告声明的条目数校验解析结果（110/111 一致）；③ 设计 18 个触发维度、8 类现象、4 级严重度的规则分类；④ 用 60 条调参集 + 40 条验证集人工评估，验证集精度约 91%，覆盖率 80%；⑤ 每个误判都写成回归测试（25 个用例）；⑥ 输出分析报告和按模块的风险清单 |
| **R** 结果 | 得出几个可执行的结论：线上 bug 中阻断级只占 5%；跨系统组合、版本回归、断线重连三类的功能级以上问题占比超过 55%；约 14.5% 的问题理论上可以被静态检查拦住。并据此整理了自己的测试设计清单和工具规划                                                                                                          |

**追问链**

1. 「为什么用规则，不用机器学习或大模型？」→ 数据量只有几千条；规则可解释，误判能写成回归测试；结果可复现。规则版可以作为以后 LLM 方案的基线和对照组。
2. 「91% 的精度怎么来的？」→ 换随机种子抽了 40 条没有参与调参的样本，人工判断严重度是否合理：32 条有判定，29 条正确。调参集和验证集分开，是为了避免自己骗自己。
3. 「S? 那 15% 怎么办？」→ 验证集里这部分大多是规则漏判，不是原文信息不足，所以我把这个标签命名为「规则未识别」。下一步打算用 LLM 做二次分类，用人工标注集评估。
4. 「这个分析有什么局限？」→ 公告是筛选和改写过的；只能看到逃逸的 bug，算不出逃逸率；推测原因无法验证。（主动说出局限，是加分项。）
5. 「如果给你公司内部的缺陷库，你会怎么做？」→ 增加「发现阶段」「是否逃逸」「根因分类」字段，做逃逸分析：哪些维度最容易逃逸，就在那些维度加测试设计和自动化。

## 四、高频问题与追问链

### （一）经历与动机

**Q1：你没有上线项目经验，怎么证明你能处理线上问题？**

- 要点：承认 → 给出补短板的具体行动（故事 A）→ 讲线上问题处理的完整闭环，见 Q9。
- 追问：「看公告和真实处理线上问题差别很大吧？」→ 是的，差别在于时效压力、信息不全、跨团队协调。我能保证的是方法正确、证据充分、沟通清楚；时效和节奏需要在真实项目里适应。

**Q2：三年在研项目，你最有成长的一件事是什么？**

- 用故事 B 或 C。重点讲**你做了什么判断和取舍**，不只是做了什么。

### （二）测试设计

**Q3：给你一个新角色，你怎么测？**

- 结构：需求评审时问的问题 → L1–L7 用例分层 → 自动化部分 → 上线后跟踪。见 [03 模块一](03_三个模块的测试设计.md)。
- 一定要举至少一个具体例子，比如七七多实例的案例，以及「测试数据要能区分对错」。
- 追问：「组合太多测不完怎么办？」→ 交互矩阵筛选 → Pairwise → 按历史严重度补三因子组合。

**Q4：一个新系统界面，你怎么测？**

- 见 [03 模块二](03_三个模块的测试设计.md) 的检查域表。重点挑「状态隔离」「规则约束」「输入方式」三个大多数候选人不会提的点。

**Q5：需求评审你会关注什么？**

- 五个维度提问：状态进出、多实例/组合、时序（暂停/打断）、异常（断线/中途退出）、边界（上限/空/超出怎么处理）。
- 例子：崩铁「谈判中途退出被判失败」，本质是需求没有定义中途退出的结果。

**Q6：测试资源有限，你怎么排优先级？**

- 按「影响 × 概率」排。影响用历史严重度：组合、回归、重连类的 S1+S2 占比超过 55%；概率用改动范围和历史热点。多语言这类量大但严重度低的，交给工具。

**Q7：回归测试范围怎么定？**

- 三个输入：改动清单（代码/配置/资源 diff）、模块依赖关系、历史缺陷热点。
- 例子：原神 2.3 更新后心海治疗多次触发、崩铁等价交换回归 → 数值基线自动化。
- 追问：「深境螺旋同一个问题出现两次，你怎么看？」→ 修 bug 不等于守护规则，要把规则变成常驻断言或服务端校验。

### （三）缺陷处理

**Q8：偶现问题怎么处理？**

- 留证据 → 统计复现率 → 二分法收敛条件 → 给规避方案 → 修复验证按复现率决定执行次数（10% 复现率至少连续 29 次不复现）。
- 追问：「开发说复现不了」→ 给复现率和证据；协助加日志；用自动化提高采样量。

**Q9：线上出了一个 bug，你怎么处理？**

1. **确认与定级**：复现，评估影响面（多少玩家、哪些平台、是否涉及付费或数据）；
2. **规避**：有没有临时规避方法（比如「重新登录可恢复」），同步给客服和运营；
3. **修复验证**：验证修复，回归相关功能；
4. **数据修复/补偿**：已受影响的数据怎么修？补偿脚本要验证不重复发、不漏发（崩铁 2.1「寰宇蝗灾」补发信用点就是例子）；
5. **复盘**：为什么漏测？补用例、补自动化、补检查项；**同类问题是否还存在于其他地方**。

- 第 4、5 步是拉开差距的地方。

**Q10：一个 bug 漏到线上了，你作为测试负责人怎么看？**

- 不推责也不揽全责：先分析是「没想到」（设计缺失）、「想到了没测」（执行/排期问题），还是「测了没发现」（环境/数据问题），针对原因改进。
- 例子：七七案例如果是「测了但两边属性接近看不出来」，就是测试数据设计问题。

**Q11：bug 怎么定级？开发不认可怎么办？**

- 定级看影响：阻断 > 功能/数据错误 > 表现 > 文本，再按影响范围和是否涉及付费调整。
- 例子：描述文本错误看起来是 S4，但如果误导了抽卡决策，就要提高优先级。
- 分歧时：用证据和玩家视角沟通；升级给负责人决策；记录结论。

### （四）自动化与工具

**Q12：你怎么选哪些东西做自动化？**

- 三个条件：高频回归、结果可判定、环境可控。数值基线、状态快照、配置检查都满足；表现类问题（特效、动作）不太满足，只能用截图对比辅助。
- 追问：「ROI 怎么算？」→ （人工执行一次的成本 × 每版本执行次数 × 版本数）对比（开发成本 + 维护成本），再加上「提前发现」的价值：越早发现，修复成本越低。

**Q13：自动化用例不稳定怎么办？**

- 区分产品偶现和用例本身不稳定；不稳定的用例隔离，不阻塞流水线，但要单独跟进；等待用条件等待，不用固定 sleep；测试数据隔离。

**Q14：你做的工具怎么推广？**

- 先解决一个具体的人的具体痛点；报错信息要能直接定位到问题；误报率要低，否则会被忽略；接进流程（CI 门禁）比靠人自觉主动使用更有效。
- 如果你有真实的推广经历 [填写]，就讲真实的。

**Q15：了解 AI / 大模型在测试中的应用吗？**

- 讲方案八：LLM 二次分类 + 评估集；需求 → 相似历史缺陷检索 → 风险清单。强调「输出是建议，要有评估集，要和规则基线对比」。
- 这对鹰角「测试开发工程师-Agent 方向」和「资深游戏测试开发工程师-工具/Agent 向」两个岗位很有用。

### （六）游戏理解

**Q16：你怎么看 XX 游戏的质量？**
