# 03 三个模块的测试设计：战斗/角色/技能、系统/UI/养成、配置/资源/构建

> 这三个模块对应你在研项目里实际负责过的方向。每个模块分四部分：数据画像 → 测试方案模板 → 复盘演练 → 和你经历的衔接。
> 「复盘演练」是面试里最好用的素材：拿一条真实的线上 bug，讲清楚「如果是我，会在哪个环节、用什么手段拦住它」。

## 模块一：战斗/角色/技能

### 数据画像（1702 条，占全部的 41.5%）

- **S2 功能/数据错误占 38.4%**，在所有模块里最高：战斗 bug 漏出去，往往是**效果算错了**，不只是看着不对。
- 触发维度 Top：偶现 21.7%、跨系统组合 8.9%、时序 7.4%、状态残留 5.2%、描述一致性 4.3%。
- 现象：功能/效果逻辑 39.1%，模型/动作/特效 34.3%。

### 测试方案模板：新角色上线

**1. 需求评审阶段：拿着这些问题去问策划和程序**

| 问题 | 来源案例 |
| --- | --- |
| 这个机制读写哪些战斗资源（能量、增益、行动序、护盾、体力）？ | 组合类 S2 占 64.6% |
| 同一个效果有两个实例时怎么处理（两个装备者、联机时双方同角色）？ | 游戏尘寰、七七、莫娜 |
| 角色在后台时哪些效果还生效？切人、死亡、复活时怎么处理？ | 状态残留类 |
| 暂停游戏、打开菜单时，计时和效果是否暂停？ | 原神暂停类问题反复出现 |
| 联机时数值取谁的属性？ | 七七按另一位玩家的攻击力计算治疗量 |
| 属性有没有阈值或分段？超过上限怎么算？ | 绝区零异常精通 600 |
| 进出副本、特殊玩法时，状态是否继承？ | 终末地庄方宜终结技能量 |
| 在特殊玩法（肉鸽、货币战争）里会被哪些规则改写？ | 崩铁货币战争光锥 |

**2. 用例分层**

| 层级 | 内容 | 方法 | 自动化可行性 |
| --- | --- | --- | --- |
| L1 描述一致性 | 描述里的每个数字都在实际结算中验证 | 三方一致性 | 高（静态检查 + 数值断言） |
| L2 单技能逻辑 | 触发条件、冷却、持续时间、层数、结束条件 | 等价类、边界值、判定表 | 高 |
| L3 状态迁移 | 切人、后台、死亡复活、进出副本、断线重连 | 状态迁移图 | 中 |
| L4 组合 | 与存量角色/装备/玩法的交互，加多实例 | 交互矩阵 + Pairwise | 高（配置驱动） |
| L5 时序窗口 | 开始/结束瞬间插入操作，暂停 | 时间轴插入 | 中（需要 GM/回调支持） |
| L6 表现 | 特效、动作、镜头 × 外观/时装 × 平台画质 | 组合抽样 | 低（截图对比可辅助） |
| L7 玩法适配 | 在各特殊玩法中的规则改写 | 场景法 | 中 |

**3. 上线后**：盯版本首周玩家反馈中这个角色相关的关键词，把新发现的问题补进 L1–L7 对应层的用例。

### 复盘演练

**演练 A：原神 2.6，多人模式下两个七七，治疗量按另一位玩家七七的攻击力计算**

- **在哪拦**：需求评审 + L4 组合层。
- **怎么拦**：评审时问「联机时同一角色出现两次，属性取谁的」；用例里固定有一条「多实例」检查：联机双方都用七七，攻击力差距拉大（比如一个 1000 一个 3000），看治疗量是否各按各的属性算。
- **为什么攻击力要拉开差距**：如果两边属性接近，就算取错了人也看不出来。**测试数据要能区分正确和错误的结果**，这一点面试时值得专门说出来。

**演练 B：终末地 03-12，莱万汀终结技即将结束的瞬间施放战技，终结技提前结束**

- **在哪拦**：L5 时序层。
- **怎么拦**：对每个有持续时间的状态，在「结束前一刻」插入其他技能。人手卡不准时间，就请程序提供 GM 命令把终结技持续时间改长、改短，或者用时间缩放放慢；自动化可以在剩余 N 帧时注入操作。

**演练 C：终末地 10-15，庄方宜开启终结技后退出副本，终结技能量没有正确继承**

- **在哪拦**：L3 状态迁移层。
- **怎么拦**：「进出副本」是状态迁移图上的一条边，它的检查项必须包括「战斗资源快照前后一致（或符合设计）」。还要问清楚设计意图：退出副本后能量应该恢复到进入前的值，还是保留副本内的变化？**先确认期望，再测实际**。

## 模块二：系统/UI/养成

### 数据画像（539 条，占 13.1%）

- **S3 表现/UI 占 60.3%**，主要现象是界面显示（69.8%）；S2 占 23.0%，其中「奖励/经济/数据」占 12.8%。
- 触发维度 Top：偶现 15.2%、**输入方式 7.8%**、**描述一致性 7.4%**、**平台 7.1%**、时序 5.0%、多人 4.6%、边界 4.1%、网络 3.5%。
- 和战斗模块的区别：系统 bug 的触发条件偏「外部环境」（输入方式、平台、网络），战斗 bug 偏「内部规则」（组合、时序）。

### 测试方案模板：一个新系统界面

| 检查域 | 检查点 | 来源案例 |
| --- | --- | --- |
| 数据正确性 | 显示值与服务端数据一致；红点与数据状态一致 | 原神 月之六：「人气奇域」打不开时按钮仍显示红点 |
| 入口与跳转 | 所有入口都能进；跳转后返回栈正确；从各入口退出后的落点 | 原神 7.0：移动端手柄进入「预下载」界面后无法退出 |
| 界面状态 | 预览、筛选、排序在关闭后应保持还是复位？**先确认设计** | 原神 5.4：排序后关闭再打开，排序未恢复默认 |
| 状态隔离 | 两个界面是否共用了同一份筛选/选择状态 | 原神 5.1：「背包-食物」页签的筛选也对「参量质变仪」的食物页签生效 |
| 规则约束 | 互斥、唯一、前置条件在所有操作路径下都成立 | 原神 月之一/月之七：深境螺旋上下半队伍编入同一角色 |
| 输入方式 × 平台 | 焦点导航、热切换、软键盘、主机系统键盘 | 终末地 07-16：编队名称、热切换问题 |
| 边界 | 空列表、满列表、长文本、字符上限、特殊字符 | 终末地：编队名称超上限、好友备注特殊字符 |
| 时间 | 倒计时、跨天刷新、活动结束时界面还开着 | 终末地 10-15：主界面倒计时异常残留 |
| 网络 | 请求中断、重复点击、回包前关闭界面 | 案例 6 |
| 多语言 | 长文本溢出、截断、换行 | 绝区零/崩铁多语言文本修复 |

### 复盘演练

**演练 D：原神 月之一 → 月之七，深境螺旋上下半队伍编入同一角色（第二次出现时导致无法开启挑战）**

- **在哪拦**：月之一修复后的**回归用例沉淀**。
- **怎么拦**：「上下半互斥」是一条业务规则，不是一个操作步骤。第一次修复后，应该把它变成**常驻断言**：每次编队数据变化后检查规则是否成立，或者在服务端加一条开挑战前的校验。然后穷举能改变编队的路径：手动拖拽、一键编队、推荐编队、复制队伍、试用角色、角色被锁定等。
- **能讲出的深度**：「修 bug 不等于修好一类问题。我会区分『修复这个 bug』和『守护这条规则』，后者要靠自动化断言或服务端校验，而不是靠下个版本人工再测一遍。」

**演练 E：原神 5.1，「背包」的食物页签筛选也对「参量质变仪」的食物页签生效**

- **在哪拦**：用例设计时加一个「状态隔离」检查。
- **怎么拦**：凡是复用了同一个 UI 组件的界面（背包、各类投入物品的选择界面），都要测「在 A 里设置的筛选/排序/选中状态，会不会泄漏到 B」。问开发：这两个界面是不是共用了同一个列表组件和状态对象？

**演练 F：终末地 07-16，编队名称的两个 bug（特定操作不显示上限提示；PS5 可超出上限）**

- 见 [02 案例 3](02_测试方法论与真实案例.md)。要点是**输入路径**和**服务端校验**。

## 模块三：配置/资源/构建（横向视角）

这不是游戏里的一个功能模块，而是**所有模块的底层输入**。它最贴近你的工具开发经历，也是测试开发岗位最常深挖的方向。

### 数据画像

- **静态可检出约 14.5%（594 条）**：文本错误、图标/描述与实际不一致、资源缺失、语音有误、解锁条件配错等。崩铁最高，为 20.1%。
- 构建/平台类的高严重度问题：
  - 终末地 06-26：部分 iOS 设备启动游戏频繁闪退或无法进入游戏（**单独发了一篇修复公告**）
  - 终末地 03-12：Android 14 部分设备使用部分功能时闪退；天玑 9300/9400/9500 芯片闪烁黑屏
  - 原神 月之八：iOS 27 Developer Beta 启动闪退
  - 绝区零 3.1：DX12 模式下首次进入游戏卡顿，更新后会重新触发一次着色器编译
  - 绝区零 1.5：iOS 机型「资源下载」中部分资源实际下载大小与显示不符

### 检查项清单

**配置检查**

| 检查项 | 能抓到的真实问题 |
| --- | --- |
| 引用完整性：外键指向的 ID 存在 | 资源缺失类、图标缺失 |
| 枚举合法性和语义：字段取值在合法集合内，且与同类条目一致 | 原神 5.3：「微光角菌」的种物类型配成「种子」，应为「孢子」 |
| 描述参数一致：描述中的数值和配置一致；描述里没有写死数字 | 原神 2.1 旅行者命座、绝区零 2.3「澄意」 |
| 跨表一致：产出配置和来源描述一致 | 原神 7.2：金蕨、植绒草、霜仙花的来源描述缺少「尘歌壶种植」 |
| 解锁条件：同类条目的条件规则一致 | 原神 7.2：薇斯纳一条语音错误地带了解锁条件 |
| 版本 diff：本版本改动的配置行全部列出，供人工复核 | 回归类 |

**资源检查**

| 检查项 | 能抓到的真实问题 |
| --- | --- |
| 图标 ↔ 模型/外观的映射一致 | 原神 1.3：鸦羽弓突破后图标与外观不一致；原神 7.2：装扮图标与实际表现不一致 |
| 引用的音效/特效/语音资源存在 | 各类「音效缺失」「特效缺失」 |
| 多语言语音资源齐全，与字幕 ID 对应 | 崩铁/原神大量「X 语语音有误」 |
| 命名、尺寸、格式、压缩、LOD 规范 | 性能/包体类 |
| 多平台/多画质档位的资源变体齐全 | 原神 3.4：胡桃特效在不同平台和画质下表现不同 |

**构建检查**

| 检查项 | 对应风险 |
| --- | --- |
| 包内资源与资源清单一致；下载大小显示与实际一致 | 绝区零 1.5 资源下载大小不符 |
| 首次启动、更新后首次启动（着色器缓存失效） | 绝区零 3.1 DX12 |
| 新系统版本、新芯片的冒烟（Beta 期介入） | iOS 27 Beta、Android 14、天玑芯片 |
| 热更新：新旧资源混用、断点续传、回滚 | JD 中的「热更新测试」 |
| 平台提审合规（主机 TRC/XR 等） | JD 中的「主机提审」 |

### 放进流水线的位置

```
提交（P4 changelist）
  └─ 提交前/提交后检查：配置格式、引用完整性、命名规范          ← 秒级，挡住低级错误
每日构建（Jenkins）
  ├─ 全量配置/资源一致性检查 + 版本 diff 报告                 ← 分钟级
  ├─ 构建 → 自动化冒烟（启动、登录、主界面、核心玩法入口）
  └─ 战斗数值基线比对（见 04 方案四）
打包前门禁
  └─ 资源清单校验、包体大小对比、多平台构建全部通过
```

### 复盘演练

**演练 G：原神 2.1，旅行者（雷）命座 6 描述是「伤害提高 100%」，实际是「造成原本 200% 的伤害」**

- **在哪拦**：配置检查（描述参数一致）。
- **怎么拦**：描述文本应该用参数模板，比如「伤害提高{0}%」，参数从配置表读取。检查器做两件事：①描述中出现的硬编码数字一律告警；②参数值和配置字段一致。这个例子里，「提高 100%」和「造成原本 200%」在数学上是同一个意思，所以**检查器还要能理解不同的表述方式**，或者要求策划统一表述规范。这正是工具做不到 100%、需要「工具 + 规范 + 人工」配合的地方，面试时讲出来能体现你对工具边界的认识。

**演练 H：终末地 06-26，部分 iOS 设备启动闪退或无法进入游戏**

- **在哪拦**：构建冒烟的机型覆盖。
- **怎么拦**：公告没有给出原因，不要猜。能讲的是流程：每次出包都在「最低支持系统版本 + 最新正式版 + 最新 Beta」三档 iOS 设备上跑启动冒烟；发生线上问题时，先按设备型号和系统版本聚合崩溃数据确认影响面，再出修复包并验证受影响的机型。

### 和你经历的衔接

这一部分最容易讲出深度，因为你确实做过：

- 你的「配置数据对比」工具：[填写：对比的是什么？两个版本之间，还是配置和某个基准之间？发现过什么问题？]
- 你的「测试证据采集」：[填写：采集了什么？日志、截图、录像、设备信息？怎么和缺陷单关联？]
- Jenkins + Perforce：[填写：你接触到什么程度？配过 Job 吗？用过 P4 触发吗？]

面试时把这些真实经历和上面的检查项清单对应起来：「我做过 X，它能覆盖其中的 A、B 两项；结合上线数据，我认为下一步最值得做的是 C，因为它对应了 N 条线上问题。」**有数据支撑的规划，比单纯描述已经做过的事更有说服力。**
