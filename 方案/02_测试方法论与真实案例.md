# 02 测试方法论 × 真实案例

> 每个案例都来自公告原文（来源标注为「游戏 版本」，可以在 `tool` 里用 `search` 命令查到原文）。
> 「为什么会漏」一栏全部是**推测**，面试时要说「我推测」，不要说成事实。

## 怎么用这份文档

面试官问「你怎么测 X」时，最有说服力的回答结构是：

**真实案例 → 抽象成一类风险 → 用什么方法系统地覆盖这类风险 → 能不能自动化 → 怎么衡量做得好不好**

下面 10 个案例都按这个结构拆。每个案例背熟「一句话版本」，深挖时再展开。

## 案例 1：状态残留——「进去时改了什么，出来时都恢复了吗」

**原始记录**

- 原神 7.2：薇斯纳在「巡游」状态下，若元素战技按键被特殊玩法按键替换，**退出相关特殊玩法后**，元素战技按键会出现异常。
- 原神 7.2：在「冰宫密令」界面**预览武器外观后**，「武器」界面的武器显示错误。
- 原神 7.2：在「游逸旅账」查看已收录的逸闻后，小道具**仍会出现**「已记录新逸闻」提示。
- 终末地 10-15：【庄方宜】开启终结技后**退出副本**时，终结技能量没有正确继承进入副本时的状态。

**拆解**：四条 bug 的共同点是「A 状态临时修改了某个共享资源，回到 B 状态时没有还原」。被修改的共享资源分别是：按键映射、武器外观数据、红点标记、能量值。

**为什么会漏（推测）**：测试通常沿着功能的主路径走（进入玩法 → 玩 → 退出），只检查玩法内部是否正确，**不检查退出后的世界是否恢复原状**。而且「特殊玩法替换按键」和「巡游状态」分别由不同的人负责，交叉点没人管。

**测试设计方法：Enter/Exit 对称性清单**

对每一个「会临时接管」的状态（特殊玩法、预览、副本、过场、拍照、载具……），列出它在进入时修改的共享资源，退出时逐项检查：

| 共享资源 | 进入时做了什么 | 退出路径 | 退出后检查 |
| --- | --- | --- | --- |
| 按键/输入映射 | 替换战技按键 | 正常退出 / 被打断 / 断线 / 角色死亡 | 按键图标和功能都还原 |
| 角色外观/模型 | 预览外观 | 关闭预览 / 切页签 / 直接退出界面 | 其他界面显示的是真实外观 |
| 红点/提示 | 标记已读 | 查看后返回 / 杀进程重进 | 红点状态与数据一致 |
| 战斗资源（能量/Buff） | 进副本快照 | 正常退出 / 中途退出 / 失败 | 与进副本前的值一致（或符合设计） |
| 镜头/UI 层级/音效 | 切换镜头、压栈 UI | 同上 | 镜头、UI 栈、BGM 还原 |

关键点是**退出路径要穷举**：正常退出只是其中一条边，被打断、断线、死亡、杀进程都是不同的边。这就是状态迁移图「每条边都走一遍」的落地形式。

**自动化思路**：做一个「状态快照 diff」工具。进入状态前对共享资源拍快照（输入映射表、角色外观 ID、红点数据、Buff/能量、UI 栈），退出后再拍一次，自动 diff，有差异就报。UE 里可以在 Functional Test 中读取 GAS 的 Attribute 和 GameplayTag，Unity 里可以用 Poco dump UI 树加业务数据接口。详见 [04 方案三](04_自动化与工具方案_UE主线.md)。

**面试深挖**

- 问：「退出路径那么多，测不过来怎么办？」→ 按风险排序：断线和死亡这类**非正常退出**优先，因为开发通常只在正常退出的回调里写恢复逻辑。数据里「状态切换/残留」维度的 S1+S2 占比是 39.1%。
- 问：「你在项目里遇到过类似的吗？」→ 用你在研项目里系统测试的真实经历回答，比如某个界面关闭后数据没刷新。没有就说没有，然后讲你会怎么查。

## 案例 2：输入方式热切换——把输入模式当成一个状态维度

**原始记录**

- 终末地 07-16：「赛跑挑战」中**进行手柄热切换操作后**，玩法倒计时异常不显示。
- 终末地 07-16：使用【探测器】后，选中标记点再进行**手柄热切换**，会重复播放道具动效。
- 原神 7.0：**移动端设备上使用手柄**，通过「设置」进入「预下载」界面后无法退出。
- 绝区零 3.2：手柄下，当[切换至上一位代理人]和[组合键触发键]**设置为同一按键**时，前者失效。
- 原神 7.0：PC 端键鼠在「千星奇域」关卡中**同时按下多个按键**，部分按键可能无响应。

**拆解**：终末地是 PC/移动/PS5 多平台同步上线的新游戏，「输入方式」维度占比 6.9%，是四款游戏里最高的。问题分三类：

1. **热切换**：切换输入设备时 UI 会重建（按键提示换图标、焦点重新分配），重建过程中丢了状态（倒计时）或重放了状态（动效）。
2. **非常规组合**：移动端 + 手柄，这是一个容易被忽略的格子。
3. **按键配置冲突**：允许玩家自定义按键，就得测冲突。

**测试设计方法：平台 × 输入方式矩阵 + 热切换插入点**

| | 触屏 | 键鼠 | 手柄 |
| --- | --- | --- | --- |
| PC | （部分设备） | 主 | 常用 |
| 移动端 | 主 | 少见 | **容易漏** |
| 主机 | - | - | 主 |

在这张表之外，再加一个**热切换插入点**清单：在计时中、动效播放中、弹窗打开时、焦点在列表中间时、文本输入中，分别切换输入设备。

**自动化思路**：UI 自动化用例按输入模式参数化。同一条用例，分别用「触屏点击 / 键鼠 / 手柄导航」三种驱动跑一遍，再插入一个「中途切换」步骤。Airtest/Poco 能做触屏和键鼠；手柄需要项目提供注入接口（GM 命令或输入模拟层）。

**面试深挖**

- 问：「手柄测试你会关注什么？」→ 焦点导航能不能到达每个可交互元素、焦点丢失后怎么恢复、按键提示图标是否随设备切换、组合键/长按、按键自定义冲突、主机平台的确认/取消键差异（不同地区的约定可能不同，以平台规范为准）。
- 问：「为什么终末地这类问题多？」→ 我推测是多平台同步上线，手柄适配和 UI 框架还在磨合期。所以如果我加入一个准备多平台上线的项目，会建议尽早把输入方式做成自动化的参数维度。

## 案例 3：输入长度边界——客户端校验 vs 平台输入路径

**原始记录**

- 终末地 07-16：特定操作导致修改编队名称时，**不显示字符上限提示**。
- 终末地 07-16：**使用 PlayStation®5 时**，编队名称可被修改至**超出字符上限**。
- 终末地 03-12：好友备注中**使用部分特殊字符**时，可输入长度异常。

**拆解**：同一个版本里修了「编队名称」的两个 bug，说明字符上限的校验至少有两条路径没覆盖到：一条是某种操作下提示不出现，一条是 PS5 的系统输入法绕过了客户端的长度限制。好友备注的问题说明「长度」本身的定义也有歧义：特殊字符算 1 个还是 2 个？

**为什么会漏（推测）**：测试只在 PC 上用键盘输入测了上限；没有测平台系统键盘的输入路径；没有定义「长度」的计算口径（字节 / UTF-16 码元 / 字形）。

**测试设计方法：边界值 × 字符等价类 × 输入路径**

| 维度 | 取值 |
| --- | --- |
| 长度 | 0、1、上限-1、上限、上限+1、远超上限（粘贴长文本） |
| 字符类型 | ASCII、中文、全角符号、emoji（含组合 emoji）、零宽字符、换行/空格、各语言特殊字符 |
| 输入路径 | 游戏内软键盘、PC 物理键盘、PS5/移动端系统键盘、粘贴、IME 候选词上屏 |
| 校验层 | 客户端实时提示、客户端提交校验、**服务端校验** |

关键问题要问开发：**服务端有没有校验？长度按什么口径算？** 只有客户端校验的话，任何绕过 UI 的输入路径都会出问题。

**自动化思路**：输入框边界值用例可以完全数据驱动；服务端校验可以在协议层直接构造请求测，不经过 UI。

**面试深挖**

- 问：「为什么特殊字符会让长度异常？」→ 不同层对「长度」的计算口径不同。比如 emoji 在 UTF-16 里占 2 个码元，组合 emoji 可能占更多，客户端按字形计数、服务端按字节计数就会不一致。
- 问：「客户端已经限制了，还需要测服务端吗？」→ 需要。PS5 这条 bug 就是客户端限制被绕过的真实例子；另外外挂和抓包改包也会绕过客户端。

## 案例 4：跨系统组合——多实例与规则交互

**原始记录**

- 崩铁 4.3：「货币战争」中，角色**同时装备**光锥「愿虹光永驻天空」**且穿戴**装备【欢愉星徽】时，光锥技能部分效果异常；修复后与技能描述一致。
- 崩铁 2.1：队伍中**有多个角色装备**光锥「游戏尘寰」时，**任意一个**装备者的【假面】结束，会导致**其他装备者**的【假面】增益也被解除。
- 原神 2.6：多人模式下**多个七七同时在队伍中**，一位玩家的七七治疗时，有概率按**另一位玩家七七的攻击力**计算治疗量。
- 原神 1.1：多人模式下队伍中**同时有两个莫娜**施放元素爆发时，泡影有小概率只生效一次。

**拆解**：这一类的 S1+S2 占比是 66.5%，所有维度里最高（存量数据维度只有 20 条，样本太少，不算）。上面四条又可以归为一个特别好讲的子类：**同一效果的多个实例**。代码里很可能用「效果 ID」做 key 存状态，于是两个实例共用了同一份数据：一个结束把另一个也清了（游戏尘寰），或者取到了另一个实例的属性（七七）。

**为什么会漏（推测）**：用例按「单个角色 + 单件装备」设计；多实例只有在联机或特定玩法（货币战争允许重复）中才会出现，而这些玩法的测试人员未必会去验证每个光锥的细节。

**测试设计方法：规则交互矩阵 + 多实例检查**

1. 新角色/新装备上线时，先列出它**读写**了哪些战斗规则：增益、能量、行动序、护盾、伤害类型。
2. 画「新规则 × 存量规则」交互矩阵，标出会读写同一个资源的格子，这些就是高风险组合。
3. 对高风险组合用 Pairwise 生成用例，把组合数从全量 N×M×K 降到可执行的规模。
4. **固定加一组多实例检查**：同一效果 ×2 来源（两个装备者、两个同名角色、联机时双方同角色），检查叠加、结束、属性取值是否各自独立。

**自动化思路**：战斗规则组合回归。用配置驱动的方式生成组合 → 在测试场景里自动摆好队伍和敌人 → 执行固定的技能序列 → 断言伤害、增益层数、持续时间。对比方式可以是**公式期望值**，也可以是**上一版本的基线快照**（后者同时能抓回归）。详见 [04 方案四](04_自动化与工具方案_UE主线.md)。

**面试深挖**

- 问：「组合爆炸怎么办？」→ 三层收敛：先用交互矩阵筛掉不共享资源的组合，再用 Pairwise 覆盖两两交互，最后对 S2 历史最多的规则（比如增益结束时机）补三因子组合。
- 问：「多实例这个点你怎么想到的？」→ 从数据里归纳出来的，四款游戏都有类似问题。这正是做缺陷模式分析的价值：把个案变成可复用的检查项。

## 案例 5：时序窗口——「即将结束的瞬间」与「暂停」

**原始记录**

- 终末地 03-12：【莱万汀】在终结技**即将结束的瞬间**施放战技，异常导致终结技提前结束。
- 原神 3.4：攀爬时，若在**体力耗尽的瞬间**打开背包界面，退出界面后角色有概率异常保持攀爬状态。
- 「暂停游戏」相关的修复在原神里反复出现：
  - 原神 1.4：通过打开菜单暂停游戏，可导致元素反应触发异常；
  - 原神 2.7：被击飞的敌人在暂停时仍会持续下坠；
  - 原神 5.2：暂停时「应战对策」进度仍会积累；
  - 原神 5.6：玛拉妮闲置动作时暂停，水豚球消失；
  - 崩铁 2.1（手柄）：米沙终结技施放过程中暂停，特效异常。

**拆解**：状态切换的边界帧存在竞态。「暂停」本质上是一个全局时间状态，每个新系统都需要正确响应它（有的用了不受暂停影响的时间源，有的在暂停期间仍在 Tick）。原神在 1.4 到 5.6 之间反复出现暂停相关问题，说明这是一个**每个新系统都要重新检查一遍的横切关注点**。

**测试设计方法：时间轴窗口插入**

对一个有持续时间的状态（技能、Buff、动画、计时器），在时间轴上取这几个点插入干扰操作：

```
开始前一刻 | 开始瞬间 | 持续中 | 结束前一刻 | 结束瞬间 | 结束后一刻
              ↑ 插入：施放其他技能 / 切人 / 打开菜单(暂停) / 受击 / 断线
```

再把「暂停/打开菜单」列为**每个新系统的固定检查项**：它的计时、物理、AI、特效在暂停时是否都停了？恢复后是否接续正常？

**自动化思路**：人手很难稳定卡到「瞬间」。可以让自动化脚本通过 GM 接口或状态回调，在状态剩余 N 帧时注入操作，并把 N 参数化（0、1、2、5 帧）；也可以对关键状态机跑随机操作（Monkey），配合录像和日志留证。

**面试深挖**

- 问：「你怎么复现『瞬间』这种问题？」→ 先找状态结束的回调或日志点，用 GM 或慢动作（时间缩放）放大窗口；再用自动化在剩余 N 帧时注入操作，统计复现率。
- 问：「怎么推动开发重视？」→ 拿数据说话：同一类问题在不同版本反复出现，说明它是横切问题，建议在框架层统一处理，或者给每个新系统加一条自动化检查。

## 案例 6：断线重连——客户端状态重建

**原始记录**

- 原神 4.2：**在水中行动时**与服务器断开连接后恢复连接，角色无法通过长按使用普攻或战技。
- 原神 7.2：**重新连接服务器后**，当前场景满足薇斯纳天赋触发条件时，无法以「巡游」状态切换登场。
- 崩铁 2.5：与 NPC「飞霄」**谈判中途退出游戏**，重新登录后直接被判定为谈判失败。
- 原神 2.2：进行每日委托时**与服务器断开连接**，重连后 NPC 有概率异常消失。

**拆解**：重连后客户端要重建状态，重建逻辑通常只覆盖「地面上、非战斗、非任务中」这类常见状态。水中、特殊形态、对话进行中，都是重建逻辑没想到的状态。崩铁的谈判 bug 是另一种问题：**中途退出时服务端怎么判定结果**，属于设计没有考虑到的情况。

**测试设计方法：状态 × 异常事件矩阵**

| 角色/流程状态 ↓ \ 异常事件 → | 断网后重连 | 杀进程重登 | 切后台过久 | 弱网高延迟 |
| --- | --- | --- | --- | --- |
| 水中/攀爬/滑翔 | | | | |
| 特殊形态（变身、载具、巡游） | | | | |
| 对话/谈判/选择中 | | | | |
| 结算界面 | | | | |
| 奖励领取请求已发出、回包前 | | | | |

每格检查：客户端显示状态是否与服务端权威状态一致？可交互性是否恢复？进度是否正确（不丢、不重复、判定合理）？

**自动化思路**：弱网工具（如 Clumsy、Network Link Conditioner 等）加上自动化脚本，在指定状态点断网/恢复，然后断言状态。「奖励请求已发出、回包前断线」这一格，最好在协议层用机器人客户端测，重点看是否重复发放。

**面试深挖**

- 问：「重连测试的重点是什么？」→ 两个一致：客户端与服务端状态一致；**重连前后的数据一致**（不丢、不重复）。涉及奖励的要重点测幂等。
- 问：「谈判失败那个怎么看？」→ 这不完全是程序 bug，是需求没有定义「中途退出」的结果。需求评审时就应该问出来，这就是测试左移。

## 案例 7：版本回归与同类问题复发

**原始记录**

- 原神 2.4：**2.3 版本更新后**，心海元素爆发期间普攻和重击命中多个敌人时，会为附近所有角色**多次**恢复生命值，与之前版本效果不同。
- 崩铁 2.7：光锥「等价交换」有概率效果异常；修复后与 **2.6 版本更新前**保持一致。
- 原神 4.2：**4.0 版本更新后**，胡桃的重击缺失部分视觉特效。
- 终末地 09-02：「**向渊行」版本更新后**，携带恢复终结技能量的战术物品进入部分关卡时，有概率异常消耗该物品。
- 原神 月之一：深境螺旋的编队界面会在上半和下半队伍**编入相同角色**（表现问题）；**原神 月之七**：同样的现象，这次**导致无法开启挑战**（阻断）。

**拆解**：前四条都是「旧功能被新版本改坏」。心海和等价交换是**数值逻辑回归**，靠人工回归很难发现，因为没人会在每个版本重新算一遍老角色的治疗次数。深境螺旋那两条更值得讲：从公告看，同类现象在月之一修过一次，月之七又出现了，而且后果更严重。根因是否相同无法从公告判断，但至少说明这个「编队互斥」规则没有被持续守护。

**测试设计方法**

1. **影响面分析**：拿到版本改动清单（提交记录、配置 diff、资源 diff），反推可能受影响的旧功能。比如改了「治疗事件的触发逻辑」，所有治疗类角色都要回归。
2. **回归基线**：给核心战斗数值建立基线快照（固定队伍 + 固定操作序列 → 伤害/治疗/能量结果），每个版本自动比对，有差异就由人判断是预期改动还是回归。
3. **修复即补用例**：每修一个 bug，就补一条能复现它的自动化用例或检查项。深境螺旋的「上下半队伍角色互斥」就该变成一条常驻断言。

**面试深挖**

- 问：「回归范围怎么定？」→ 三个输入：改动清单（代码/配置/资源 diff）、模块依赖关系、历史缺陷热点。再按风险分层：核心链路全量自动化，改动相关模块人工深测，其余抽样。
- 问：「回归基线 diff 有差异，怎么区分是 bug 还是设计改动？」→ 和版本改动说明交叉核对：有对应改动说明的标记为预期，没有的必须找到负责人确认。基线要能「接受更新」，否则会一直误报。

## 案例 8：描述 vs 配置 vs 实际结算

**原始记录**

- 原神 2.1：旅行者（雷）命之座 6 层**描述**写的是「伤害提高 100%」，**实际效果**是「造成原本 200% 的伤害」——修的是描述。
- 终末地 03-12：干员【艾维文娜】潜能【恩威并施】**与描述不符**，修复后**实际效果**与描述一致——修的是逻辑。
- 绝区零 2.3：「危局强袭战」增益「澄意」**描述文本错误**，实际为生命值上限 +25%、贯穿伤害 +15%。

**拆解**：同样是「描述与实际不一致」，有时改描述，有时改逻辑。这一类有 256 条（6.2%），S2 占 17.2%。核心问题是**同一个数值存在三个地方**：描述文本、配置表、代码逻辑，三者没有自动对齐。

**测试设计方法：三方一致性**

| 来源 | 内容 | 获取方式 |
| --- | --- | --- |
| 描述文本 | 「伤害提高 100%」 | 多语言文本表 |
| 配置 | `DmgBonus = 1.0` | 技能/Buff 配置表 |
| 实际结算 | 伤害公式里的实际乘区 | 战斗日志或自动化断言 |

人工测试时，**每个描述里的数字都要在实际结算中验证**，不能只看效果「有没有触发」。

**自动化思路**：这就是你做「配置数据对比」的自然延伸——写一个检查器，从描述文本中抽出数值和占位符（多数项目的描述是模板 + 参数，例如 `{0}%`），与配置表字段比对。模板化的项目里可以检查「描述里写死了数字，但没有引用参数」这种危险写法。详见 [04 方案一](04_自动化与工具方案_UE主线.md)。

**面试深挖**

- 问：「描述错了算严重吗？」→ 看是否影响玩家决策：抽卡和养成的决策是根据描述做的，描述把效果写高了，等于误导消费，问题就严重。所以这类问题即使「不影响实际效果」，也不能一律当成低优先级。

## 案例 9：数值/容量边界

**原始记录**

- 绝区零 1.4：异常精通属性值**已达到 600** 的情况下，继续提升所带来的增益效果**低于预期**。
- 崩铁 2.6：背包中部分遗器、道具、材料**数量大于等于上限**时，有概率**无法进入部分关卡**（S1）。
- 终末地 03-12：提交醚质时若**超出提交上限**，提交进度显示异常；修复后超出部分保留、不提交。
- 原神 1.1：**武器数量达到上限时**，在商城购买武器的提示内容错误。

**拆解**：上限处的行为本身就容易没定义清楚：超出部分怎么处理？满背包时奖励怎么发？阈值之后公式是否分段？崩铁那条最典型：一个系统（背包）的边界状态，阻断了另一个系统（关卡入口）。

**测试设计方法**

- **数值边界**：阈值前后取点（599/600/601），检查公式有没有分段、分段点是否连续。
- **容量边界作为账号状态**：准备一批「边界账号」，比如满背包、满货币、满好友、0 体力、0 货币，日常回归时用这些账号走主流程，检查其他系统会不会被影响。
- **超出处理要先定义**：需求评审时就问清楚，满了之后是丢弃、转邮件，还是禁止操作。

**面试深挖**

- 问：「满背包测什么？」→ 所有会产出物品的入口：任务奖励、邮件、商店、掉落、合成、活动兑换。还有不产出物品但会检查背包的入口（例如进入关卡前的检查），崩铁那条 bug 就是这一类。

## 案例 10：偶现问题与平台差异

**原始记录**

- 原神 2.2：进行世界任务「清籁逐雷记」时，**进入多人游戏模式有概率**导致任务无法完成；更新后仍遇到的玩家退出并重新登录即可继续。
- 终末地 03-12：搭载**天玑 9300/9400/9500** 芯片的 Android 设备，在部分战斗场景有概率**闪烁黑屏**。
- 终末地 03-12：部分系统版本为 **Android 14** 的设备，使用部分功能时有概率闪退。
- 原神 月之八：**iOS 27 Developer Beta** 的设备启动游戏会闪退。
- 原神 月之四：开启「角色动态高精度」后，切换部分角色时游戏卡顿或闪退；同版本另一条：**不支持该选项的设备**也异常显示了这个选项。
- 原神 3.4：胡桃元素爆发命中特效的修复，在 **PS5/PS4 Base/PS4 Pro/PC/iOS/Android × 画质档位**上各有不同表现。

**拆解**：「概率/偶现」占 16.9%，是数量最多的维度，S1+S2 占 46.3%。平台问题则集中在特定芯片（GPU 驱动）、新系统版本、设置项的支持判断这几类。

**偶现问题的处理流程**

1. **先留证据**：日志、录像、设备信息、账号、时间点、前置操作。这是你做过的「测试证据采集」可以直接对接的地方。
2. **统计复现率**：同一条件跑 N 次，记录成功/失败次数，比如「10 次复现 3 次」。
3. **收敛条件**：二分法排除变量，比如换机型、换账号、去掉前置操作、单人/联机，直到找到必现或高概率条件。
4. **给出规避方案**：比如「退出并重新登录可恢复」，便于客服和运营在修复前处理线上反馈。
5. **修复后验证**：用至少同样次数（通常更多）的执行证明复现率降到 0。

**平台矩阵怎么建**：按「芯片/GPU 厂商 × 系统大版本 × 内存档位」分层抽样机型，再加两类专项：**新系统 Beta 预检**（iOS/Android 新版本一出 Beta 就跑冒烟），以及**设置项支持判断**（每个画质/特性开关在不支持的设备上是否隐藏、是否回落）。

**面试深挖**

- 问：「偶现 bug 开发说复现不了怎么办？」→ 给复现率和证据，不给结论；协助开发加日志埋点；用自动化跑循环提高采样量；必要时约定「下次复现时保留现场」的流程。
- 问：「机型那么多怎么选？」→ 按用户占比 + 芯片代表性 + 历史问题机型三个维度选；新芯片和新系统版本要单独关注，数据里天玑芯片和 iOS Beta 都是真实例子。

## 附：把这些方法串起来（被问「你的测试设计方法论是什么」时）

> 「我的做法是**风险驱动**的。拿到需求后，先用功能分解覆盖主路径，这是基本功；然后用一份**条件维度清单**做第二遍检查，包括状态进出、输入方式、平台、组合、时序、边界、网络异常、版本回归。这份清单来自我对 4000 多条上线修复记录的归纳，每个维度都有历史案例和对应的测试方法。最后按历史严重度给维度排优先级：组合、回归、重连这几类出真错误的比例超过一半，优先投入设计和自动化；多语言这类量大但严重度低的，交给静态检查工具批量处理。」
