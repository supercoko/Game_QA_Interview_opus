# 04 自动化与工具方案（UE 为主线，附 Unity 对照）

> 原则：**每个方案都要能指向数据里的一类真实问题**。面试官问「为什么做这个工具」时，你的回答是「因为上线数据里有 N 条这类问题」，而不是「因为别人也在做」。
> 代码均为**示意代码**，用来说明设计思路；`QATestHooks`、`FStateSnapshot` 这类名字是假设的项目内接口，实际要看项目提供了什么。

## 总体：游戏测试的分层

| 层 | 手段 | 反馈速度 | 主要拦截的问题（对应数据） |
| --- | --- | --- | --- |
| L0 静态检查 | 配置/资源/文本检查，接 CI | 秒–分钟 | 静态可检出的 14.5%：描述不一致、资源缺失、图标错误、文本错误 |
| L1 逻辑测试 | 战斗公式、规则的单元/数据驱动测试 | 分钟 | 数值错误、组合规则 |
| L2 引擎内功能测试 | UE Functional Test / Unity PlayMode | 分钟–小时 | 状态残留、组合回归、时序窗口 |
| L3 客户端 UI 自动化 | Airtest/Poco，按输入方式参数化 | 小时 | 界面跳转、输入热切换、红点 |
| L4 设备矩阵 | 真机冒烟、兼容性巡检 | 小时–天 | 平台差异、机型、系统版本 |
| L5 线上监控 | 崩溃聚合、玩家反馈关键词 | 实时 | 逃逸问题，再反哺前面各层 |

**越往下越贵、越慢，所以能在上层拦住的不要留到下层。** 这是讲「自动化 ROI」时的基本逻辑。

## 方案一：配置一致性检查器（L0，最贴近你的经验）

**针对的数据**：静态可检出 594 条（14.5%），以及描述/表现不一致 256 条。

**设计**

```
配置表导出(CSV/JSON) ─┐
文本表(多语言)    ─────┼─> 加载层（按 schema 解析） ─> 规则引擎（插件式） ─> 报告 + 退出码
资源清单          ─────┘                              ├─ RefIntegrity    引用完整性
                                                      ├─ EnumCheck       枚举合法性
                                                      ├─ DescParamCheck  描述参数 = 配置值
                                                      ├─ HardcodedNumber 描述里写死的数字
                                                      ├─ CrossTable      跨表一致（产出 vs 来源描述）
                                                      └─ DiffReport      本版本改动行清单
```

**核心代码（示意）**

```python
import re
from dataclasses import dataclass

@dataclass
class Issue:
    level: str      # error / warn
    rule: str
    where: str      # 表名:行ID:字段，要能直接定位到单元格
    message: str

PLACEHOLDER = re.compile(r"\{(\w+)\}")
NUMBER = re.compile(r"(?<![\w{])\d+(?:\.\d+)?%?")

def check_desc_params(skill_rows, text_table):
    """描述用参数模板时：模板里的参数都必须在配置中存在；描述里不应出现写死的数字。"""
    issues = []
    for row in skill_rows:
        tpl = text_table.get(row["desc_key"])
        if tpl is None:
            issues.append(Issue("error", "DescParam", f"skill:{row['id']}", f"文本 key 不存在: {row['desc_key']}"))
            continue
        for name in PLACEHOLDER.findall(tpl):
            if name not in row["params"]:
                issues.append(Issue("error", "DescParam", f"skill:{row['id']}", f"描述引用了不存在的参数 {name}"))
        stripped = PLACEHOLDER.sub("", tpl)
        for num in NUMBER.findall(stripped):
            issues.append(Issue("warn", "HardcodedNumber", f"skill:{row['id']}",
                                f"描述中写死了数字 {num}，请确认是否应引用配置参数"))
    return issues

def check_refs(rows, field, valid_ids, table):
    return [Issue("error", "RefIntegrity", f"{table}:{r['id']}:{field}", f"引用的 {r[field]} 不存在")
            for r in rows if r[field] and r[field] not in valid_ids]
```

**落地要点（面试深挖的重点）**

| 问题 | 做法 |
| --- | --- |
| 误报太多，策划不愿意用 | 规则分 error/warn 两级，只有 error 会挡提交；支持白名单和「基线」（存量问题不阻塞，只拦新增）；报错信息必须定位到「表名:行ID:字段」 |
| 配置格式经常变 | 用 schema 驱动加载，不要在规则里写死列号 |
| 全量检查太慢 | P4 提交时只检查改动的表和行（增量）；每日构建跑全量 |
| 怎么证明有用 | 统计每月拦截数、误报率，以及「本应在 QA 阶段才发现的问题」被提前拦下的比例 |
| 什么做不了 | 语义等价（「提高 100%」和「造成原本 200%」是一回事）需要统一表述规范，或者人工复核。这是工具的边界 |

## 方案二：本地化与语音资源检查（L0）

**针对的数据**：多语言/本地化 306 条（7.5%），几乎全是 S3。数量大、严重度低，正适合交给工具批量处理。

| 检查 | 方法 |
| --- | --- |
| 占位符一致 | 各语言译文的 `{0}`、`<color>` 等标签集合与原文相同，标签正确闭合 |
| 长度膨胀 | 译文长度 / 原文长度超过阈值时告警，配合 UI 控件宽度做溢出风险提示 |
| 伪本地化 | 构建一个把所有文本加长 30–40% 并加上特殊字符的「伪语言」，提前暴露截断和编码问题 |
| 语音资源存在 | 每条带语音的台词，在每种语音语言下都有对应文件 |
| 语音时长异常 | 同一台词在不同语言下的语音时长比例偏离过大时告警，可以发现截断或配错文件。终末地 07-16 修过「英语时部分剧情语音播放不完整」 |
| 人称代词等语义问题 | 工具做不了，留给人工；可以按「代词 + 角色性别表」做简单提示 |

## 方案三：状态快照 diff（L2，UE Functional Test）

**针对的数据**：状态切换/残留 156 条（S1+S2 占 39.1%），以及案例 1 中的按键替换、预览残留、副本能量继承。

**思路**：进入临时状态前对共享资源拍快照 → 进入 → 按某条路径退出 → 再拍快照 → diff。

```cpp
// 示意：放在测试地图里的 Functional Test，每个实例配置一种「状态 × 退出路径」
UCLASS()
class AStateResidueTest : public AFunctionalTest
{
    GENERATED_BODY()
protected:
    virtual void StartTest() override;

    UPROPERTY(EditAnywhere, Category = "QA") FName StateToEnter;  // 如 SpecialPlayMode / WeaponPreview / Dungeon
    UPROPERTY(EditAnywhere, Category = "QA") FName ExitPath;      // Normal / Interrupted / Death / Reconnect

    FStateSnapshot Before;     // 项目自定义的快照结构
    FTimerHandle Handle;
};

void AStateResidueTest::StartTest()
{
    Super::StartTest();
    // 快照内容：当前生效的输入映射、角色 GameplayTag 和关键属性（若用 GAS）、UI 栈、外观 ID、红点数据
    Before = FStateSnapshot::Capture(GetWorld());
    QATestHooks::EnterState(GetWorld(), StateToEnter);
    // 实际实现中，等待和退出需要用 Timer/Tick 分步推进，不能在 StartTest 里同步完成
    GetWorldTimerManager().SetTimer(Handle, [this]()
    {
        QATestHooks::ExitState(GetWorld(), StateToEnter, ExitPath);
        const TArray<FString> Diffs = Before.Diff(FStateSnapshot::Capture(GetWorld()));
        FinishTest(Diffs.IsEmpty() ? EFunctionalTestResult::Succeeded : EFunctionalTestResult::Failed,
                   FString::Join(Diffs, TEXT("\n")));
    }, 2.0f, false);
}
```

命令行运行（接 CI）：

```bat
UnrealEditor-Cmd.exe MyGame.uproject -ExecCmds="Automation RunTests Project.Functional Tests;Quit" ^
    -unattended -nopause -nullrhi -log -ReportExportPath="D:\qa\report"
```

**要讲清楚的设计点**

- **快照里放什么**：不是越多越好。先从历史问题最多的几类开始：输入映射、Tag/Buff、UI 栈、外观。快照项太多，会被大量「预期内的变化」淹没。
- **期望不一定是「完全恢复」**：有些状态在退出后就应该改变（比如副本里消耗的道具）。所以每个状态要配一份「允许变化的字段」白名单，这份白名单本身就是需求澄清的产物。
- **退出路径参数化**：同一个状态 × 4 条退出路径 = 4 个测试实例，覆盖的就是状态迁移图上的 4 条边。

**Unity 对照**：用 Unity Test Framework 的 PlayMode 测试（`[UnityTest]` 返回 `IEnumerator`，用 `yield return` 等待帧），快照通过游戏内的调试接口获取；UI 层级可以用 Poco 的 `poco.agent.hierarchy.dump()` 导出后做 diff。

## 方案四：战斗规则组合回归 + 数值基线（L1/L2）

**针对的数据**：跨系统组合 212 条（S1+S2 占 66.5%）、版本回归 37 条（56.8%）。例子包括心海 2.3 回归、等价交换回归、游戏尘寰多实例。

**流水线**

```
组合生成（Python, Pairwise） -> 用例 JSON（队伍/装备/敌人/操作序列）
   -> 引擎内执行器（UE Functional Test 读取 JSON/DataTable，摆场景、执行操作）
   -> 战斗事件日志（伤害、治疗、增益增减、能量变化）
   -> 与「公式期望」或「上一版本基线」比对 -> 差异报告
```

**组合生成与基线比对（示意）**

```python
from allpairspy import AllPairs   # pip install allpairspy

chars = ["七七", "莫娜", "新角色X"]
weapons = ["武器A", "武器B"]
modes = ["单人", "联机-双方同角色"]       # 多实例作为一个显式维度
cases = [dict(char=c, weapon=w, mode=m) for c, w, m in AllPairs([chars, weapons, modes])]

def compare(result: dict, baseline: dict, tol=1e-6):
    diffs = []
    for key, expect in baseline.items():           # key 如 "heal_total" / "buff_stacks@t=5s"
        got = result.get(key)
        if got is None or abs(got - expect) > tol * max(1, abs(expect)):
            diffs.append(f"{key}: 基线 {expect} -> 本次 {got}")
    return diffs
```

**要讲清楚的设计点**

| 难点 | 做法 |
| --- | --- |
| 随机性（暴击、概率触发） | 测试模式下固定随机种子，或者通过 GM 关闭暴击，否则基线不可比 |
| 结果来源 | 读战斗事件日志，**不读 UI 上的数字**。UI 数字是表现层，本身也可能出错 |
| 执行速度 | 用时间缩放加速，或者在逻辑层直接驱动战斗（不渲染） |
| 基线更新 | 版本改动说明里列出的数值变化 → 人工确认后「接受新基线」；没列出的变化一律当疑似回归 |
| 测试数据能区分对错 | 联机双方的同一角色要配差异很大的属性，否则取错了对象也看不出来（七七案例） |

**UE 落地**：Functional Test 从 DataTable 或 JSON 读取用例，生成角色和敌人，通过项目的 GM 或测试钩子释放技能；需要在真机上跑时，用 Gauntlet（`RunUAT RunUnreal`）把测试会话部署到设备上。

**Unity 对照**：PlayMode 测试加上 NUnit 的 `[TestCaseSource]` 做数据驱动。

## 方案五：按输入方式参数化的 UI 自动化（L3，Airtest/Poco）

**针对的数据**：输入方式/热切换 101 条；系统/UI 模块中输入方式占 7.8%。终末地这一维度占 6.9%，四款游戏里最高。

```python
import pytest

class InputDriver:                       # 统一接口，用例不关心具体输入方式
    def confirm(self): ...
    def back(self): ...
    def focus(self, node): ...           # 触屏/键鼠：直接点击；手柄：方向键导航到目标

class TouchDriver(InputDriver): ...      # poco(node).click()
class KeyMouseDriver(InputDriver): ...   # 键鼠事件
class GamepadDriver(InputDriver): ...    # 项目内输入注入接口（GM），或虚拟手柄

@pytest.mark.parametrize("driver_cls", [TouchDriver, KeyMouseDriver, GamepadDriver])
@pytest.mark.parametrize("switch_at", [None, "timer_running", "effect_playing", "popup_open"])
def test_race_challenge(poco, driver_cls, switch_at):
    d = driver_cls(poco)
    enter_race_challenge(d)
    if switch_at:
        wait_until(switch_at)
        hot_switch_input(to=other_input(driver_cls))     # 热切换插入点
    assert poco("CountdownText").exists(), "倒计时消失"  # 终末地 07-16 的真实问题
```

**要讲清楚的设计点**

- **用例和输入方式解耦**：用例只写「确认/返回/聚焦到某节点」，三种 Driver 各自实现。新增一种输入方式时，用例不用改。
- **手柄注入**：最稳定的方式是项目在输入层提供注入接口（GM）；外部虚拟手柄驱动也可以，但在不同平台上的维护成本高。
- **Poco 和 UE**：Poco 需要在游戏里接入对应引擎的 SDK 才能拿到 UI 树。你在项目里怎么接入的，就怎么讲；接入不了的部分可以用 Airtest 图像识别兜底，但要说清楚它的不稳定性。

## 方案六：偶现问题的循环执行与证据采集（L2/L3）

**针对的数据**：概率/偶现 693 条（16.9%，S1+S2 占 46.3%），数量最多的维度。这里可以直接对接你做过的「测试证据采集」。

**功能**

1. 对指定场景循环执行 N 次，记录每次的通过/失败；
2. **失败时自动采集**：失败前 30 秒的录像（环形缓冲）、客户端日志、设备信息、账号、时间点、操作序列；
3. 输出复现率和环境分布，帮助收敛条件（比如失败全部集中在某个机型）。

**一个能体现深度的点：修复验证要跑多少次？**

如果原问题的复现率是 p，修复后连续 n 次都不复现，「其实没修好却碰巧一次都没复现」的概率是 (1-p)^n。要把这个概率压到 5% 以下：

| 原复现率 p | 需要连续通过的次数 n |
| --- | --- |
| 30% | 9 |
| 10% | 29 |
| 5% | 59 |
| 1% | 299 |

> 面试时可以这样说：「偶现问题的修复验证，我会先估算原复现率，再决定跑多少次。复现率 10% 的问题，至少连续跑 29 次不复现，才有 95% 的把握。这种量级只能交给自动化。」

## 方案七：CI 集成（Jenkins + Perforce）

**你接触过 Jenkins 和 Perforce，这一部分重点讲「怎么把前面的检查串起来」。**

```groovy
// Jenkinsfile 示意
pipeline {
  agent { label 'win-build' }
  triggers { pollSCM('H/10 * * * *') }       // 或用 P4 插件 / P4 trigger 回调
  stages {
    stage('Sync')         { steps { p4sync credential: 'p4-cred', source: depotSource('//depot/MyGame/...'), populate: autoClean() } }
    stage('Static Check') { steps { bat 'python -m cfgcheck --changed-only --fail-on error' } }
    stage('Build')        { steps { bat 'RunUAT.bat BuildCookRun -project=... -platform=Win64 ...' } }
    stage('Smoke')        { steps { bat 'UnrealEditor-Cmd.exe ... -ExecCmds="Automation RunTests Project.Smoke;Quit" ...' } }
    stage('Combat Baseline') { steps { bat 'python run_combat_baseline.py --compare last-good' } }
  }
  post {
    failure { /* 机器人通知：失败阶段 + changelist 区间 + 提交人 + 报告链接 */ }
    always  { archiveArtifacts artifacts: 'report/**' }
  }
}
```

**要讲清楚的设计点**

- **失败归因**：报告里列出上次成功到本次失败之间的 changelist 区间和提交人，让问题直接找到负责人。
- **不稳定用例隔离**：自动化用例本身也会偶现失败。连续出现不稳定结果的用例放进隔离区，不阻塞流水线，但每天单独跟进；否则大家很快就会忽略告警。
- **门禁分级**：静态检查的 error 挡提交；冒烟失败挡出包；数值基线差异只通知不阻塞，由人确认。

## 方案八：缺陷知识库与风险推荐（bug_insight 的延伸，对应 Agent 方向岗位）

**现状**：[tool/](../tool/README.md) 已经能做到：解析 → 规则分类 → 统计 → 按模块输出风险清单 → 关键词检索。

**下一步**

| 阶段 | 做什么 | 怎么评估 |
| --- | --- | --- |
| 1 | 用 LLM 给「S? 规则未识别」的 624 条做二次分类 | 人工标注 100 条做评估集，比较规则、LLM、规则 + LLM 三种方案的精度和召回率 |
| 2 | 输入需求文档或改动说明，检索相似的历史缺陷（向量检索 + 关键词），生成本需求的风险清单 | 让测试人员给推荐结果打分（是否相关、是否有启发），统计 precision@k |
| 3 | 接入团队真实的缺陷管理系统，增加「发现阶段」「是否逃逸」字段，做逃逸分析 | 逃逸率、各维度的逃逸占比变化 |

**要讲清楚的设计点**

- **LLM 的输出是建议，不是结论**：风险清单由人确认后才进入用例；评估集要固定下来，每次改 prompt 都要重跑评估。
- **为什么第一版用规则**：数据量小、要可解释、要能写回归测试。规则版是 LLM 版的基线和对照组。

## UE ↔ Unity 对照表

| 需求 | UE | Unity |
| --- | --- | --- |
| 逻辑单元测试 | Automation Test（`IMPLEMENT_SIMPLE_AUTOMATION_TEST`）、Automation Spec | Unity Test Framework EditMode（NUnit） |
| 场景内功能测试 | Functional Testing（地图中放置 `AFunctionalTest`） | UTF PlayMode（`[UnityTest]`） |
| 命令行运行 | `UnrealEditor-Cmd ... -ExecCmds="Automation RunTests ..."` | `Unity -batchmode -runTests -testPlatform PlayMode -testResults ...` |
| 设备上运行 | Gauntlet（`RunUAT RunUnreal`） | UTF 可构建 Player 在目标平台上运行 PlayMode 测试 |
| 资源/配置检查 | Data Validation 插件（Editor Validator）、Commandlet、Editor Python（`unreal` 模块） | `AssetPostprocessor`、Editor 脚本 + `-executeMethod`、Addressables Analyze |
| UI 自动化 | Poco（需接入 SDK）/ 项目自研 / Automation Driver 插件 | Poco（UnityPoco，UGUI/NGUI）、Airtest 图像识别 |
| 截图对比 | Screenshot Functional Test | Graphics Test Framework 包或自研 |
| 性能分析 | Unreal Insights、`stat` 命令、CSV Profiler | Unity Profiler、Memory Profiler、Frame Debugger |
| 构建 | UAT `BuildCookRun` | `BuildPipeline.BuildPlayer` + `-executeMethod` |

**从 UE 迁移到 Unity 时的说法**：「测试分层、数据驱动、快照 diff、基线比对、CI 门禁这些设计都和引擎无关，差别在接入层：UE 是 C++/蓝图加 Automation 框架，Unity 是 C# 加 NUnit。我在 UE 上做过 Functional Test，换到 Unity 上要补的是 UTF 的 API 和 Unity 的资源管线，方法论可以直接复用。」

> 上表列的是各引擎的通用能力。具体 API 和参数随引擎版本变化，面试前用你熟悉的版本核对一遍，**只讲你真的跑通过的部分**。
