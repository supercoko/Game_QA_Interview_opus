# 01 上线 Bug 模式分析：4104 条修复记录里看到了什么

> 数据：原神 53 篇、崩铁 31 篇、绝区零 20 篇、终末地 7 篇，共 111 篇官方公告、4305 条记录；统计口径为官方「修复/修正」类条目，共 **4104 条**。
> 工具：[tool/](../tool/README.md)，完整报告见 [output/分析报告.md](../output/分析报告.md)。下文数字都来自该报告。

这份文档是整套方案的「事实底座」。面试时，你的测试方法、自动化和工具方案都要能追溯到这里的某条数据或某个案例上，这样聊的是有证据的判断，而不是背出来的方法论。

---

## 一、先说结论（面试时 30 秒版本）

> 「我把四款上线游戏两年多的 4000 多条修复记录做了结构化分析，最大的发现是：漏到线上的 bug 绝大多数不是主流程问题，而是**条件依赖型问题**。阻断级只占 5%；有一半能明确识别出触发条件，集中在跨系统组合、时序、状态残留、输入设备、平台差异这些维度；其中**跨系统组合、版本回归、断线重连**这三类的功能级以上问题占比都超过 55%。所以我认为测试设计的重点，应该从『功能点有没有覆盖』转向『条件维度有没有覆盖』。另外约 14.5% 的问题理论上靠配置/资源静态检查就能拦住，这正好是我做工具的方向。」

---

## 二、七个关键发现

### 发现 1：线上 bug 以表现问题为主，阻断问题很少

| 严重度（按现象推断） | 条目 | 占比 |
| --- | ---: | ---: |
| S1 阻断/崩溃（无法推进、卡死、闪退、无法进入） | 205 | 5.0% |
| S2 功能/数据错误（效果、数值、奖励、进度） | 1213 | 29.6% |
| S3 表现/UI/音频 | 1911 | 46.6% |
| S4 文本/文案 | 151 | 3.7% |
| S? 规则未识别 | 624 | 15.2% |

**怎么解读**：主流程的阻断问题大多在上线前就被拦住了，漏出去的是长尾。长尾问题靠「多投人力多点几遍」效率很低，要靠两件事：**系统化的条件维度**（发现 2、3）和**低成本的批量检查手段**（发现 6）。

### 发现 2：一半的问题有明确触发条件，而且分布高度集中

18 个触发维度里，排在前面的是（一条 bug 可以属于多个维度）：

| 触发维度 | 条目 | 占比 | 典型案例 |
| --- | ---: | ---: | --- |
| 概率/偶现 | 693 | 16.9% | 原神 2.6：多人模式两个七七同队，治疗量**有概率按另一位玩家七七的攻击力计算** |
| 多语言/本地化 | 306 | 7.5% | 崩铁 4.7：韩语语音下多个任务的对话语音有误 |
| 描述/表现与实际不一致 | 256 | 6.2% | 终末地 03-12：干员【艾维文娜】潜能【恩威并施】与描述不符 |
| 时序/特定操作组合 | 215 | 5.2% | 终末地 03-12：【莱万汀】终结技**即将结束的瞬间**施放战技，导致终结技提前结束 |
| 跨系统组合 | 212 | 5.2% | 崩铁 4.3：货币战争中，同时装备光锥「愿虹光永驻天空」并穿戴【欢愉星徽】时光锥效果异常 |
| 状态切换/残留 | 156 | 3.8% | 原神 7.2：薇斯纳的战技按键被特殊玩法按键替换，**退出玩法后按键异常** |
| 多人/联机 | 139 | 3.4% | 原神 4.1：多人模式水中传送后，队友已获取的异色生物能力仍显示为未获取 |
| 平台/设备差异 | 132 | 3.2% | 终末地 03-12：天玑 9300/9400/9500 芯片 Android 设备在部分战斗场景闪烁黑屏 |
| 输入方式/热切换 | 101 | 2.5% | 终末地 07-16：「赛跑挑战」中**手柄热切换**后倒计时不显示 |
| 边界值/数量上限 | 89 | 2.2% | 崩铁 2.6：背包遗器/道具达到上限时，有概率**无法进入部分关卡** |

另有 28% 的条目只写了「特定情况下」，其中 712 条没有任何其他线索，这是公告措辞造成的信息损失。

### 发现 3：组合、回归、重连三类最容易出「真错误」

各维度中 S1+S2（阻断 + 功能/数据错误）的比例：

| 触发维度 | 条目 | S1+S2 占比 |
| --- | ---: | ---: |
| 存量数据/已受影响数据 | 20 | 70.0% |
| **跨系统组合** | 212 | **66.5%** |
| **网络/重连/登录** | 64 | **57.8%** |
| **版本回归** | 37 | **56.8%** |
| 时序/特定操作组合 | 215 | 47.0% |
| 概率/偶现 | 693 | 46.3% |
| 边界值/数量上限 | 89 | 46.1% |
| 状态切换/残留 | 156 | 39.1% |
| …… | | |
| 多语言/本地化 | 306 | 0.0% |

**怎么解读**：维度的「数量」和「严重度」是两回事。

- **多语言量大但几乎都是 S3** → 适合用静态检查和工具批量处理，不值得投入大量人工。
- **组合、回归、重连量不大但严重** → 值得投入资深测试的设计精力和自动化回归。

测试资源分配的依据就在这张表里。面试被问「测试资源有限时怎么排优先级」，可以直接拿它回答。

### 发现 4：战斗是最大的模块，它的风险集中在组合和时序上

| 模块 | 条目 | 占比 | 该模块 Top 维度 |
| --- | ---: | ---: | --- |
| 战斗/角色/技能 | 1702 | 41.5% | 偶现 21.7%、组合 8.9%、时序 7.4%、状态残留 5.2% |
| 系统/UI/养成 | 539 | 13.1% | 偶现 15.2%、输入方式 7.8%、描述一致性 7.4%、平台 7.1% |
| 玩法/活动 | 533 | 13.0% | 偶现 12.6%、描述一致性 8.6%、组合 5.8% |
| 音频/语音 | 448 | 10.9% | 多语言 50.9% |

- 战斗模块的 S2 占 38.4%，是所有模块里最高的：战斗 bug 漏出去，往往是**效果算错了**，不只是看着不对。
- 系统/UI 模块 S3 占 60.3%，主要现象是界面显示（69.8%），触发条件偏向**输入方式和平台**，这和战斗模块完全不同。

→ 两个模块的测试策略应该不同，详见 [03 三个模块的测试设计](03_三个模块的测试设计.md)。

### 发现 5：游戏特性决定风险画像

| 游戏 | 明显偏高的维度 | 推测原因 |
| --- | --- | --- |
| 终末地（新游戏，多平台同步上线） | 时序 13.0%、平台 7.6%、输入方式 6.9%、S1 占 8.4% | 上线初期多平台和手柄适配还在磨合 |
| 原神 | 偶现 22.9%、多人 5.5%、位置/地形 5.1%、外观 3.8% | 大世界 + 联机 + 物理交互 |
| 崩铁 | 多语言 11.8%、静态可检出 20.1% | 回合制战斗逻辑相对确定；剧情语音量大（四种语音） |
| 绝区零 | 玩法/活动占 21.3% | 版本里独立玩法多（迷宫诡域、零号空洞等） |

**怎么解读**：没有放之四海而皆准的测试策略。去面一个项目之前，先想清楚它的产品特性，再推断它的风险画像。比如面终末地，就要主动聊多平台、手柄、时序；面原神，就要聊联机和大世界物理。

### 发现 6：约 14.5% 的问题理论上靠静态检查就能拦住

594 条命中了「文本错误、图标与实际不一致、描述与效果不一致、资源缺失、语音有误、解锁条件配错」等特征（崩铁 20.1%，原神 12.3%）。典型例子：

- 原神 2.1：旅行者（雷）命之座 6 层描述写的是「伤害提高 100%」，实际效果是「造成原本 200% 的伤害」——**描述文本和逻辑配置不一致**
- 原神 5.3：材料「微光角菌」的洞天种物类型配成了「种子」，应为「孢子」——**枚举字段配错**
- 原神 7.2：薇斯纳的一条语音错误地带了解锁条件——**解锁条件配置错误**
- 原神 1.3：武器「鸦羽弓」突破后图标与外观不一致——**资源映射错误**
- 绝区零 2.3：「危局强袭战」增益「澄意」的描述文本与实际数值不符

**怎么解读**：这些问题不需要跑游戏，配置/资源的交叉校验就能发现，而且校验可以接进 CI，每次提交都跑。这和你做过的「配置数据对比」工具是同一个方向，详见 [04 自动化与工具方案](04_自动化与工具方案_UE主线.md) 方案一。

### 发现 7：修 bug 不只是改代码，还要修已经受影响的数据

20 条修复明确提到了已受影响的玩家或数据：

- 崩铁 2.1：完成「寰宇蝗灾」存护Ⅱ剧情后拿不到信用点 → 两周内为已遇到问题的玩家**补发**
- 原神 2.8：阅读教程后有小概率拿不到原石 → 更新后把未发放奖励的条目**重置为有红点的状态**
- 崩铁 1.6：1.5 版本更新后击败「次元扑满」拿不到奖励 → 已遇到的玩家再次击败即可获得

这类修复的 S1+S2 占比达 70%。线上问题处理的完整闭环是：**修复代码 → 修复存量数据 / 补偿 → 验证补偿脚本不重复发、不漏发 → 补回归用例**。面试问「线上出了 bug 你怎么处理」，答到这一层就能和只会说「复现、提单、回归」的候选人拉开差距。

## 三、方法和局限（被追问时要能讲清楚）

### 方法

1. **解析**：按「版本 → 原文分类 → 条目」解析 Markdown；每个版本的解析条数都和公告声明的条数核对（110/111 一致，原神 2.0 原帖正文是图片）。
2. **打标签**：18 个触发维度、8 类现象、4 级严重度，都用关键词正则实现，多标签。
3. **评估**：
   - 调参集 60 条：修规则前严重度判定精度 45/48 ≈ 94%；
   - 验证集 40 条（换随机种子，没参与调参）：覆盖率 80%，精度 29/32 ≈ 91%；
   - 未识别的 8 条中 7 条是规则漏判，所以这个标签叫「规则未识别」，不叫「信息不足」。
4. **回归**：每个误判修好之后都写成单元测试（目前 25 个），保证以后改规则不会把它改坏。

### 局限（主动说出来，比被问倒强）

- 公告是**经过筛选和改写的公开信息**，不等于内部缺陷库：严重问题可能另发公告，大量小问题可能根本不写，措辞还会被模糊化。
- 只能看到「漏到线上的 bug」，看不到「测试阶段拦住的 bug」，所以**算不出逃逸率**，只能描述逃逸缺陷的分布。
- 每个版本的条目数受写法影响，不能当成质量趋势。
- 规则是关键词匹配，语义判断有误差，比例只能看大致分布。
- 「为什么漏测」的原因分析都是推测，没有内部信息可以验证。面试时要说「我推测」「可能的原因是」，不要说成事实。

## 四、这份分析怎么用

| 场景 | 用法 |
| --- | --- |
| 写测试用例前 | 用 `checklist --module` 生成对应模块的风险清单，逐个维度过一遍 |
| 需求评审时 | 用「组合 / 状态 / 时序 / 平台 / 输入」五个维度向策划和程序提问 |
| 定测试优先级 | 参考发现 3：S1+S2 占比高的维度优先投入设计和自动化 |
| 选工具方向 | 参考发现 6：静态可检出的问题优先做成 CI 检查 |
| 面试 | 用发现 1–7 作为「我对游戏质量的理解」的事实支撑 |
