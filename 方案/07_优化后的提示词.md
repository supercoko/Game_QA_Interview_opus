# 07 优化后的提示词

## 原提示词里不清楚的地方

| 问题 | 影响 | 改进 |
| --- | --- | --- |
| 没说目标岗位是业务测试、测试开发还是专项测试 | JD 里三类都有，准备的素材差别很大 | 写明主攻方向和次要方向 |
| 没说要什么形式的产出 | 只要文档，还是也要代码 | 写明交付物清单和存放位置 |
| 没说引擎侧重 | 你的经验是 UE，目标项目多是 Unity | 写明以哪个引擎为主线 |
| 没说自己负责过哪些模块 | 案例没法和你的经历对应起来 | 列出模块，并附一两个真实的工作细节 |
| 没说明数据文件的结构和局限 | AI 可能把公告当成完整的缺陷库 | 简要说明数据来源和局限 |
| 没有诚信约束 | AI 可能帮你「包装」出不存在的经历 | 明确要求不得虚构经历，推测要标注 |
| 「能深挖」没有定义 | 产出可能停留在方法论层面 | 定义成「案例 → 方法 → 自动化 → 追问链」 |
| 没有准备时间 | 行动计划无法排期 | 写明可用时间 |

## 改进后的提示词

> 把 `〔 〕` 里的内容换成你的实际情况再用。

```text
# 背景
我是游戏测试工程师，3 年经验，全部在一个〔UE〕在研项目（未上线）：
- 业务测试：负责〔战斗/角色/技能、系统/UI/养成〕的功能测试；
- 工具开发：用 Python 做过〔配置数据对比、测试证据采集〕，用过 UE Functional Test、Airtest/Poco，接触过 Jenkins 和 Perforce。
- 一两个真实细节：〔例如：配置对比工具对比的是两个版本的 Excel 导出，发现过 X 类问题〕
短板：没有上线经验，没有处理真实线上 bug 的经历，工具没有真实的数据反馈。最近面试结果不理想。

# 资料（只读取当前文件夹，不要访问文件夹之外的任何信息）
- 「原神 / 崩铁 / 绝区零 / 终末地 … 问题修复分类索引.md」：四款上线游戏官方更新公告中「问题修复」章节的整理，按版本 → 公告原分类 → 条目组织。
  注意：这是公开、经过筛选和改写的信息，不是完整的缺陷库，看不到内部原因。
- 「官方岗位详情快照.md」：目标公司的岗位 JD。
- 「个人能力和经验简单介绍.md」：我的经历概述。

# 目标岗位
主攻：游戏测试工程师（系统/战斗向），用工具能力做差异化；次要：游戏测试开发（UE 项目）。
不考虑：5 年以上的资深岗、管理岗、纯平台全栈岗。

# 要求
1. 先用代码把四份索引解析成结构化数据，按「触发条件维度 / 现象 / 严重度 / 模块」分类统计；
   分类规则要人工抽样评估精度（调参集和验证集分开），并写单元测试。
   这个工具本身要能作为我的作品，在面试中演示和深挖。
2. 基于数据写出：
   a. 关键发现（每条都有数字和真实案例支撑，标注来源版本）；
   b. 测试方法 × 真实案例：每个案例按「拆解 → 可能漏测的原因（标注为推测）→ 测试设计方法 → 自动化思路 → 面试追问及回答要点」展开；
   c. 针对我负责过的模块的测试方案模板和「如果是我会怎么拦住」的复盘演练；
   d. 自动化与工具方案：以 UE 为主线，附 Unity 对照，每个方案指向数据中的一类问题，包含示意代码和落地难点；
   e. 面试材料：自我介绍、STAR 故事模板、高频问题追问链、各岗位匹配度；
   f. 〔3〕周行动计划，每天可用〔2–3〕小时。
3. 底线：
   - 不得虚构我的经历和数字；需要我补充的地方用 [填写] 占位，并给出引导问题；
   - 推测必须标注为推测；
   - 引用的案例必须核对过版本和原文。
4. 交付：代码放 tool/，生成结果放 output/，文档放 方案/，全部用中文 Markdown。
5. 开始前，如果有影响方向的不明确之处，先列出问题并给出推荐选项让我选择。
```

## 为什么这样改

- **背景 + 短板写具体**：AI 才能把案例映射到你的真实经历上，而不是给出泛泛的方法论。
- **说明数据的局限**：防止产出把公告当成完整缺陷库，得出过度的结论（比如「逃逸率」）。
- **底线条款**：面试被深挖时，虚构的内容是最大的风险。把「不虚构、标注推测、核对引用」写进提示词，比事后检查可靠。
- **交付物写清楚**：避免来回确认，也方便以后复用同一套结构分析别的数据。
