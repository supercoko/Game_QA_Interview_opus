## 一、原稿核心问题诊断（以业务端游戏测试视角）

如果你投递的是**业务端游戏测试工程师**（如米哈游业务测试、鹰角系统向/关卡向/战斗向游戏测试），原稿目前存在 5 个明显的转化率隐患：

| 维度 | 原稿现状 | 对面试官/筛选的影响 | 优化方向 |
| :--- | :--- | :--- | :--- |
| **1. 叙事重心倒挂（最关键）** | 前 16 行全是工具开发与自动化，业务测试和跨项目支援被压在最后且篇幅很短。 | 业务向用人主管容易误判为“偏测开、不想做业务测试”或“核心业务测试深度不够”。 | **重构板块顺序**：先立住“扎实业务测试 + 白盒根因定位 + 上线期项目支援”的底盘，再用“配置监控、静态检查与自动化”作为高壁垒加分项。 |

#### 三、配置质量保障与内部效能工具建设（质量左移）

- **DataTable 配置变更自动检测与确认闭环（独立设计并落地）**：
  - **背景痛点**：项目迭代中策划频繁修改配置表，QA 难以实时感知改动范围，易引发漏测与配置回归问题。
  - **技术方案**：基于程序提供的引擎导出接口，独立搭建全链路检测管线——通过 Perforce `change-commit` 触发 Jenkins，执行机借助 UGS 同步至目标 CL 后调用 UE 蓝图导出 DataTable JSON；采用任务串行排队机制保障执行机状态隔离，并将 CL 与配置快照持久化至 MongoDB。
  - **差异闭环与运维**：使用 Python + `DeepDiff` 实现“单文件维度历史基线对比”（对比本次改动文件与其上一次历史变更快照，而非机械对比相邻 CL），在 Web 端可视化展示变更并支持**责任人确认闭环**与**同表任意两版本历史 Diff**；结合飞书多维表维护的“资源路径—QA 负责人”映射精准通知对应人员；Pipeline 异常时实时告警并支持人工重触发恢复。
- **FlowGraph 策划配置静态检查**：
  - 针对 FlowGraph 配置错误难以在运行前暴露的问题，负责 **XML 到 JSON 的结构解析**及核心节点的 Python 静态检查规则开发，并将检查结果接入入库、Web 展示与飞书告警通知，将部分低级配置缺陷拦截在运行测试之前。
- **内部 QA 质量平台建设与流程卡点**：
  - 基于开源框架二次开发内部质量 Web 平台（Vue3 + Flask + MongoDB），统一整合 **Checklist、自动化执行结果、配置 Diff 与问题反馈**，减少测试信息分散；
  - 针对提交流程痛点，开发提交工具的**单据关联校验、单据状态/提交人核验及任务提醒**功能，规范提测与提交纪律；后期结合 AI 辅助完成部分历史代码重构与现有平台能力接入。

#### 四、自动化测试实践与持续集成回归

- **战斗核心链路自动化冒烟（UE Functional Test + Jenkins）**：
  - **目标**：解决战斗模块快速迭代期间，核心 AI 行为与基础攻击/伤害链路易被误改且人工回归耗时的问题。
  - **落地**：基于 UE Functional Test 编排角色与怪物基础攻击场景，调用程序/中台接口控制 AI 状态、触发攻击并读取生命值完成自动化断言；接入 Jenkins 持续集成，通过 Python 脚本提取失败摘要、推送告警通知并留存完整执行日志，实现核心链路劣化及时预警。
- **采集物常规流程自动化验证（Airtest + Poco，阶段性实践）**：
  - 基于配置坐标与朝向，通过 GM 指令传送并调整相机视角，结合 Poco 触发交互操作；以控件状态与奖励弹窗作为表现层断言依据，自动留存运行日志、截图、录像及 Airtest HTML 报告，沉淀常规采集场景回归能力并明确特殊场景下的自动化边界。
