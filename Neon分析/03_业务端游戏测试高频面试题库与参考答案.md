## 模块二：简历核心业务经历深挖（100% 必考，已全面扩容）

### Q4：如果让你全面设计【物品、背包与快捷背包系统】的测试方案（参考原神背包架构），你会怎么系统拆解？
- **考察意图**：检验你是否分得清**“物品本体规则”**与**“背包容器管理”**的职责边界，有没有体系化的状态矩阵、配置边界和防刷安全思维。
- **高分回答框架（四层清晰拆解，杜绝“获取与堆叠混为一谈”）**：

#### 第一层：物品本体属性与静态配置（Item 配置矩阵）
先把“一个物品是什么、允许干什么”拆透，重点测**属性开关的排列组合**与**静态展示配置**：
1. **图标与基础展示配置**：
   - 物品 ID、名称、描述/背景文本（超长文本折行、富文本变色、多语言截断）、品质/星级与底框颜色匹配、**图标配置**（大图标/小图标/详情图是否正确映射、缺图时的默认兜底图、不同分辨率/UI 缩放下的清晰度）、页签归属与“获取来源跳转”。
2. **四大核心属性开关矩阵（极易因组合遗漏出 Bug）**：
   - **可否使用（Usable）**：不可直接使用（如纯突破材料、任务凭证，详情页应隐藏/禁用“使用”按钮） vs 可直接使用（食物、自选箱、消耗品、功能小道具）。
   - **可否消耗（Consumable）**：使用后扣除数量（如回血食物、经验书、体力药） vs **可使用但不消耗**（参考原神小道具：留影机、寻宝罗盘、化种匣——可反复触发效果但不扣数量）。
   - **可否堆叠（Stackable）**：不可堆叠（单占一格，通常为带唯一实例 GUID 和独立属性的武器/圣遗物） vs 可堆叠（带堆叠上限配置：如 `1`、`999`、`9999` 或特殊约定 `-1` 无限堆叠，以及对应的角标显示规则）。
   - **可否丢弃/摧毁（Discardable）**：不可丢弃（核心任务道具、已锁定/已装备道具，应隐藏或拦截销毁操作） vs 可丢弃/摧毁（二次确认弹窗、销毁是否按配置返还基础货币/材料）。
   - **关键组合交叉校验**：如“不可使用但可消耗（仅由合成/养成/任务扣除）”“可使用但不消耗 + 带冷却 CD”“不可丢弃但可消耗”，逐一核验前端按钮显隐、后端接口拦截和提示文案是否一致。

#### 第二层：物品生命周期核心操作（获取 → 使用/效果/CD → 消耗 → 丢弃）
按一个物品从诞生到离场的完整链路逐段验证：
1. **获取（Acquire）**：
   - 多途径产出（大世界采集/怪物掉落、任务奖励、商店购买、邮件/活动领取、合成转换、GM 发放）；
   - 获取表现（侧边获得飘字、首次获得弹窗/图鉴点亮、新道具红点提示）；
   - 溢出兜底策略（超出单种物品持有上限或背包总容量上限时：拦截拾取并提示、自动转邮件、还是进临时背包）。
2. **使用与使用效果（Use & Effect）**：
   - **使用前置校验**：目标状态校验（如复活类道具仅对阵亡角色生效、回血道具对满血角色是否拦截、饱食度/增益上限校验）、场景状态校验（战斗中/联机/副本/攀爬/游泳/演出中是否禁用）；
   - **批量使用**：单次使用 vs 滑动条批量使用（`1` / 部分 / `上限` / 超过持有量），批量开随机箱/自选箱的产出结算；
   - **效果生效校验**：即时收益（回血、复活、加体力、解锁外观/功能、发放货币或子道具）、持续 Buff（同类型 Buff 是刷新时长、顶替覆盖还是数值叠加）、功能型道具触发（释放场景物件、扫描周围目标、切换交互状态）；
   - **消耗与失败回滚**：可消耗道具扣减后若数量归 `0`，格子正确移除且详情页焦点不悬空；不可消耗道具数量不变；**当服务端校验失败或超时，客户端表现、数量、效果和 CD 必须完整回滚**。
3. **使用后进入 CD（Cooldown）**：
   - **独立 CD vs 共享 CD**：单个道具独立冷却 vs 同组道具共享冷却（参考原神：不同复活料理共享 120s CD，同系功能小道具冷却策略）；
   - **CD 实时同步与禁用**：背包界面与**快捷栏/快捷背包**的 CD 阴影遮罩与倒计时必须完全同步，冷却中点击应拦截并给出清晰提示；
   - **CD 持久化与边界防漏洞**：下线重登、切换场景/进出副本、角色死亡、联机切换主机，以及**客户端修改本地系统时间**时，CD 必须以服务端时间戳（或严谨的游戏内计时机制）为准，防止清零刷效果或永久卡死 CD。
4. **丢弃 / 销毁（Discard）**：
   - 单选/多选/数量滑块边界（`0` / `1` / `当前上限`）；丢弃后数量、容量与筛选列表实时刷新；若丢弃道具正绑定在快捷栏，快捷栏同步清空或置灰；任务/锁定道具禁止被误丢弃。

#### 第三层：背包容器管理与快捷背包（Container & Quick-Slot）
把容器本身的组织、存储、检索与快捷使用拆开测：
1. **分类页签与容量体系**：分页签独立容量（如原神武器/圣遗物/材料/食物/小道具/任务/贵重道具各页签规则）与总容量上限校验；接近上限警告与满包限制。
2. **堆叠与分格管理（容器存储规则）**：堆叠上限边界（`0`、`1`、`max-1`、`max`、`max+1`、`-1` 无限堆叠）、满堆叠自动拆新格、手动拆分/合并（若支持）、消耗后空格回收与大数值格式化（如 `9999+`、防整型溢出）。
3. **排序、筛选与锁定**：多维度排序（品质、数量、等级、获取时间）及同权重项的稳定二次排序；筛选/切页签状态下使用或丢弃道具后列表不错位；加锁/解锁状态联动防消耗防销毁。
4. **快捷背包 / 快捷栏绑定**：绑定、替换、解绑操作；绑定道具消耗至 `0` 后的表现（置灰保留 vs 卸下）以及重新获取后是否自动恢复；快捷触发时的 **CD 同步**、操作打断与键鼠/手柄快捷键提示切换。

#### 第四层：跨系统耦合、前后端一致性与极限性能
1. **跨系统状态互斥**：角色处于死亡、受击硬直、攀爬、游泳、钩锁飞行、变身、对话演出、切图 Loading 期间，打开背包、使用道具或按快捷栏的互斥与打断表现。
2. **前后端一致性与防刷安全**：高频连点使用/丢弃/拆合防“扣一次生效两次”或数量变负；弱网、断线重连、使用瞬间强杀客户端后，核对重登时客户端展示与服务端真实存量完全一致。
3. **性能与多端适配**：千级物品塞满背包时的打开耗时、快速滚动帧率与内存波动；PC 键鼠拖拽/右键 vs Xbox/PS5 手柄焦点移动、翻页和长按确认体验。

### Q5：你主负责过【商店系统（购买、恢复 CD）】和【红点系统（纯客户端存档）】，这两个系统各自最容易踩哪些坑？
- **考察意图**：这两个系统看似基础，却是线上资损（超买/刷货）和玩家体验投诉（消不掉的幽灵红点）的超级重灾区。
- **高分回答思路**：
  - **一、商店系统核心测试点（购买 + 恢复 CD）**：
    1. **购买校验与资产边界**：货币刚好等于价格、差 1 不足、多币种组合/折扣价取整；限购次数边界（单次购买上限、剩余库存 `1`、`0`、`-1` 不限购）；满包购买的兜底逻辑（拦截购买还是发邮件，且绝不能“扣钱不发货”）。
    2. **刷新与恢复 CD（高频高危点）**：
       - 商品限购恢复 CD / 商店定时刷新（日刷/周刷/月刷/固定间隔恢复）；
       - **在线跨刷新点**：玩家停留在商店界面跨越零点或恢复 CD 归零瞬间，库存和价格是否自动实时刷新（防显示旧库存报错或买成旧商品）；
       - **防改时间作弊**：修改本地客户端时间前调/后调，验证恢复 CD 和限时上架严格以**服务端时间**校验。
    3. **并发与弱网安全**：弱网下疯狂连点“购买”，服务端必须做好幂等/锁控，防止突破限购上限或把货币扣成负数；购买瞬间断线重连后，核对货币扣除与背包入账严格一致。
    4. **关联联动**：购买道具后背包、红点、任务收集进度（如“获得某道具”）是否即时联动。
  - **二、红点系统核心测试点（尤其针对“纯客户端存档”机制！）**：
    1. **出现与消失核心逻辑**：触发红点的前置条件（如获得新物品、商品刷新、满足解锁条件）与消除条件（点击查看、点进子页签、消耗完毕、过期失效）是否严格闭环，杜绝“点进去什么都没有却消不掉的**幽灵红点**”和“明明有可领内容却不亮的**漏亮红点**”。
    2. **纯客户端存档的 4 个必测高危坑（面试极加分！）**：
       - **卸载重装 / 清本地缓存 / 换新设备登录**：本地存档丢失后，历史老内容如何初始化？会不会导致老玩家上线满屏红点爆炸，或者真正的新内容丢失红点？
       - **同设备多账号切换登录**：本地红点存档**必须按账号 UID / 服务器隔离存储**！否则 A 账号点消了红点，切到 B 账号直接被误消（或把 A 的红点串到 B 账号）。
       - **异常杀进程/断电写入损坏**：红点状态变更时强制杀进程，本地存档文件是否损坏或丢写，重登后状态是否正常回退/保留。
       - **跨端登录不一致**：PC 与手机/主机先后登录同一账号时，由于纯客户端存档不同步，需评估设计预期是否符合规范（如重要强提示红点是否应由服务端下发状态而非纯本地记录）。
    3. **树状层级聚合与性能**：子红点 → 页签红点 → 主界面入口红点的父子联动（支持数量型红点与普通圆点混用时的聚合计算，子项全部消除后父节点必须即时熄灭）；高频获物/批量操作时不因红点全树遍历导致界面卡顿。

### Q6：你主负责过 3C【相机 + 钩锁】以及【大世界交互物及交互工具】，怎么系统设计它们的测试点？
- **考察意图**：3C 和大世界交互直接决定动作/开放世界游戏的核心手感与防卡死底线。
- **高分回答思路**：
  - **一、相机系统（Camera）**：

    2. **多交互物重叠与优先级**：采集物、NPC、机关、掉落物紧挨时，交互列表排序、滚轮/手柄方向键切换焦点及默认高亮项合理性。

### Q12：FlowGraph 静态检查你们设计了哪些规则？发现了什么典型问题？静态检查的局限/误判怎么处理？
- **考察意图**：米哈游/鹰角极其看重“策划数据配置检查”，看你对静态分析的设计深度与务实认知。
- **高分回答思路**：
  1. **7 类通用 Python 检查规则（XML → JSON 解析后校验）**：
     - **图拓扑链路类**：① 节点首尾是否为合法 `Start` / `End`（连线闭环检测）；② **死循环检测**；③ 前置/后置条件完整性校验；
     - **参数与引用类**：④ 参数类型校验；⑤ 参数范围校验；⑥ 空参数检测；⑦ 参数引用有效性（校验所填 ID/资源是否存在）。
  2. **真实拦截数据与杀手级案例**：
     - 接入入库、Web 展示与飞书通知后，在前期策划不熟悉规范阶段**单日检出 30+ 条错误**，其中 **50% 以上为链路结构问题**，其余为参数配置问题；
     - **典型真实案例**：两条并行任务线路中，策划在 A 线路生成怪物，却误配到 B 线路去销毁该怪物——静态检查直接精准报错“A 线路生成怪物未销毁”与“B 线路销毁不存在的怪物”，同时大量拦截了缺 `Start/End` 节点和死循环，把原本要跑进游戏才能撞出的低级阻断提前清零。
  3. **高阶工程认知：静态检查的误判边界（极大加分点！）**：
     - **真实遇到的误判**：当图链路中存在环路、但环路内部配了**条件跳出节点**时，静态图分析无法在运行前判断该跳出条件在运行时是否必然成立，容易将其误报为死循环；
     - **工程解法与分工**：将“无任何出口的绝对死环”定为强报错阻断，将“含条件出口的环路”降级为弱警告/人工复核（或白名单标记），避免误报刷屏导致策划麻木；同时明确分工——**静态检查拦确定性结构/配置错，运行时实测验动态上下文、时序并发和玩家体验**。

## 模块五：技术基础高频考题（网络 / Linux / SQL / Python / Lua / 跨引擎）

### Q22：TCP 和 UDP 在游戏里一般怎么选？弱网测试怎么模拟、重点测什么？
- **核心答点**：
  - **TCP vs UDP**：TCP 可靠有序，适合**登录、背包、商店、支付、任务、聊天**等对数据绝对准确要求高、容忍轻微延迟的业务；UDP（常配合 KCP/QUIC/自研可靠 UDP）低延迟无队头阻塞，适合**动作战斗、钩锁位移、多人实时位置同步**等强实时模块。
  - **弱网模拟**：使用 Clumsy、Fiddler/Charles 限速、移动设备弱网工具或引擎内置弱网参数，模拟**高延迟（200ms~1000ms）、丢包（5%~30%）、抖动、限带宽、Wi-Fi↔4G/5G 切换及短/长断网**。
  - **核心关注**：超时提示与防界面卡死、断线重连后的全状态同步（血量/位置/CD/背包/变身/任务/引导）、弱网连点服务端幂等防刷、客户端预测失败时的回滚表现不瞬移穿地。

### Q23：Linux 常用排障命令与数据库（SQL / MongoDB）基础怎么考？
- **考察意图**：米哈游多数业务测试 JD 明确标注“熟悉 Linux、数据库操作优先”，且你在技术栈里也已掌握。
- **必会核心点**：
  1. **Linux 日志与环境排障**：
     - 实时追踪：`tail -f server.log`
     - 查 UID/关键字上下文：`grep -n -C 5 "10086" server.log`（压缩日志用 `zgrep`）
     - 统计高频报错：`grep "ERROR" server.log | awk '{print $4}' | sort | uniq -c | sort -nr`
     - 查进程/端口/资源：`ps -ef | grep game`、`ss -tunlp` / `netstat -tunlp`、`top`、`df -h`、`free -m`
  2. **MongoDB vs MySQL 选型理解（结合你的真实项目）**：
     - 我在内部质量平台和 DataTable 快照存储选了 **MongoDB**，因为游戏配置表 JSON 结构动态多变、嵌套深，文档型数据库天然适配配置快照、Diff 结果与自动化报告；
     - **MySQL** 等关系型数据库强在 ACID 事务、强一致性和复杂联表，更适合订单、玩家核心资产流水等强结构化数据。
  3. **SQL 高频查询手熟**：`SELECT ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...`、`INNER JOIN` vs `LEFT JOIN` 区别、索引的作用与避免大表全表扫描意识。

### Q24：Python 与 Lua 基础（及阅读 TS/C++ 代码排障）高频考题
- **高频易考点**：
  - **Lua（客户端查 Bug 极高频）**：
    1. Table 兼具数组部分（**下标从 1 开始**）和哈希部分；
    2. `ipairs` 遇 `nil` 即停，`pairs` 遍历全表无序——数组中间删元素直接赋 `nil` 形成空洞，是导致背包/列表漏显的经典坑；
    3. **真假值陷阱**：Lua 中仅 `false` 和 `nil` 为假，**`0` 和空串 `""` 均为真**（排查配置参数逻辑极易踩雷）；
    4. 元表 `metatable` 与 `__index`（常用于配置表默认值回退与只读保护）。
  - **Python（工具开发主力）**：
    1. 深浅拷贝（`copy` vs `deepcopy`，做配置 Diff 基线时防原地修改）；
    2. 可变默认参数坑、`dict`/`set`（$O(1)$）与 `list`（$O(n)$）查找效率差异（写静态检查与大表比对性能关键）；
    3. 实用代码题准备：如“流式逐行读取 1GB 日志文件，用 `collections.Counter` 统计 Top 10 报错码”（不一次 `readlines()` 撑爆内存）。
  - **阅读 TS / C++ 的业务定位价值**：面对服务端或引擎逻辑缺陷，能顺着日志报错栈直接追到对应条件分支（如死亡校验跳过同步），把提单从“表象猜谜”升级为“精准根因定位”。

### Q29：如果线上发生了漏测事故（如配置改坏或状态同步 Bug 流出），你会怎么做复盘？
- **考察意图**：看你能不能把一次事故转化为“不依赖个人细心”的系统防呆机制。
- **高分回答思路（5 步标准复盘）**：
  1. **止损优先**：第一时间定位影响范围、协助验证热更/配置回滚/开关兜底方案，不急着甩锅追责。
  2. **双维度根因拆解**：分清**技术根因**（为何出 Bug）和**漏测根因**（需求没对齐？用例盲区？提测后临时改表没感知？环境差异？）。
  3. **固化防呆机制（结合你的真实工作流极其亮眼！）**：
     - 临时改表漏感知 → 纳入 **DT 变更自动追踪与负责人确认**；
     - 确定性配置/链路错 → 沉淀为 **FlowGraph 静态检查新规则**；
     - 同类逻辑/边界盲区 → 更新用例与 Checklist，并借助 **AI 历史 Bug 库分析**扫描同类历史风险；
     - 高频核心回归 → 评估沉淀到 `Functional Test` 冒烟。
  4. **横向举一反三**：排查其他相似模块是否存在同一类隐患（如一个界面漏判 `-1` 无限堆叠，全项目涉堆叠界面一并排查）。
  5. **落地可验证 Action Item**：明确整改负责人、截止时间与验收标准，并在组内分享复盘。
