# bug_insight：上线游戏缺陷模式分析工具

把四款上线游戏（原神、崩铁、绝区零、终末地）更新公告里的「问题修复」条目解析成结构化数据，按**触发维度 / 现象 / 严重度 / 模块**打标签，再生成分析报告和按模块划分的风险清单。

做这个工具是为了回答一个问题：**上线后才被修掉的 bug，都是在什么条件下出现的？测试设计应该往哪些维度多想一步？**

## 运行

只依赖 Python 标准库（3.10+），不用装第三方包。

```bash
cd tool
# 本机 python 命令不可用时，可以用 uv：uv run --python 3.13 python -m bug_insight analyze
python -m bug_insight analyze                         # 导出数据并生成报告和清单 -> ../output/
python -m bug_insight search 手柄 --game 终末地        # 按关键词/游戏/模块/维度/严重度检索
python -m bug_insight search --trigger combo --severity S2 --limit 20
python -m bug_insight checklist --module "系统/UI/养成" # 生成单个模块的风险清单
python -m bug_insight sample -n 40 --seed 99          # 随机抽样，用于人工评估规则精度
python -m unittest discover -s tests -t .             # 跑单元测试
```

输出：

| 文件 | 内容 |
| --- | --- |
| `output/bugs.csv` | 全量结构化数据（UTF-8 BOM，Excel 可以直接打开） |
| `output/bugs.jsonl` | 同上，JSON Lines 格式 |
| `output/分析报告.md` | 概览、严重度、模块、触发维度、交叉分析、代表案例 |
| `output/checklists/*.md` | 各模块风险清单：按历史频率排序的检查维度，附历史案例 |

## 结构

```
bug_insight/
  parser.py    解析 Markdown -> Section / Bug，并把解析条数和公告声明条数对比做校验
  taxonomy.py  分类规则：18 个触发维度、8 类现象、严重度推断、模块归一化、静态可检出判定
  analyze.py   打标签、统计、挑代表案例、导出 CSV/JSONL
  report.py    生成报告和风险清单
  cli.py       命令行
tests/
  test_parser.py    解析器单测，外加真实数据冒烟（解析条数与声明条数一致）
  test_taxonomy.py  分类规则回归用例（人工抽检发现的每个误判都写成一条用例）
```

## 设计取舍

- **为什么用规则，不用模型**：数据量只有几千条；规则可解释，每条误判都能写成回归用例；不依赖外部服务，结果可复现。规则覆盖不到的条目（S? 约 15%）适合以后交给 LLM 做二次分类，再用人工标注集评估效果。
- **多标签**：一条 bug 常常同时属于「手柄 + 热切换 + 倒计时」等多个维度，单标签会丢信息。
- **统计口径**：只统计官方公告中以「修复/修正」开头的条目，排除「优化/调整」和崩铁 1.1/1.2 的玩家整理帖。
- **数据校验**：每个版本解析出的条数都和公告声明的「提取 N 条」比对，111 篇公告中 110 篇一致（原神 2.0 原帖正文是图片，原始索引里就没有条目）。

## 精度评估

| 样本 | 用途 | 严重度判定覆盖率 | 判定精度 |
| --- | --- | --- | --- |
| 60 条（seed=2026） | 调规则用 | 修规则前 48/60 | 修规则前 45/48 ≈ 94% |
| 40 条（seed=99） | 验证集（没有参与调参） | 32/40 = 80% | 29/32 ≈ 91% |

- 验证集里 8 条落在「S? 规则未识别」，其中 7 条是规则漏判，只有 1 条是原文信息不足，所以这个标签叫「规则未识别」，不叫「信息不足」。
- 触发维度在验证集上大约有 1 条误判（「快速支援」是绝区零的技能名，被误当成时序操作），已修复并补了用例。
- 验证之后又补了几条通用规则，所以当前版本的精度**没有重新评估**；要报新数字，需要再抽一份新的验证集。

## 局限

- 公告只公开了一部分修复内容，措辞也经过运营处理（如「特定情况下」），这份数据不等于真实的缺陷库。
- 每个版本的条目数受公告写法影响很大，不能直接当成质量趋势。
- 关键词规则对「描述有误但不影响效果」这类语义判断会有误差，看比例、看趋势可以，不要当成精确值。

## 可以继续做的

1. 用 LLM 对「S?」条目做二次分类，用人工标注的 100 条评估精度和召回率，再和规则版对比。
2. 输入需求文档或改动说明，按模块和关键词召回相似的历史缺陷，生成「本需求的风险检查清单」（RAG 思路）。
3. 接入团队缺陷管理系统的 API（Jira/TAPD 等），用真实缺陷数据替换公告数据，增加「发现阶段」「是否逃逸」等字段，做缺陷逃逸分析。
4. 输出 HTML 看板，按版本对比维度分布的变化。
